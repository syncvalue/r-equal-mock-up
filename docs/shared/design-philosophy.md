# 設計思想（設計者の想定）— エンジニアへの引き継ぎ

**この文書の目的**: このモックの**画面と各種ドキュメント**を、エンジニアに渡すとき、設計者の**想定（なぜそうしたか、何を守ってほしいか）**を、きちんと伝える。**開発自体は、エンジニアが行う**。エンジニアも、開発では Claude Code などの AI を使う前提。

- **設計者の指示は、ここに、日付つきで足していく**（追記のルールは、末尾）。
- 仕様の本文は、機能別の `docs/features/*/spec.md`。ここには、機能をまたぐ**考え方・判断の原則**を書く。入口は [INDEX.md](../INDEX.md)。
- 食い違ったときの優先順位: **テスト・コード ＞ 仕様書 ＞ README ＞ この文書**（この文書は、方針。具体の振る舞いは、仕様書が正）。

---

## このモックの位置づけ

- **モックは、画面と仕様を固めるためのもの**。外部サービス・サーバーはなく、localStorage とダミーデータで動く（[全体像](overview.md)）。**いまは、まず、画面を確定させる**ことに集中している。**バックエンドの設計は、いまはしない**（2026-11-18）。
- **正式版の方向**: バックエンドは**API形式で提供し、フロントエンドがそのAPIを使う**、という分離を考えている。**言語・DB・認証方式は、まだ決めていない**（PHP・Node.js など、未定。エンジニアが決めてよい）。決めたら、各機能のフォルダに `data.md`・`api.md` を足す想定。
- **モックの画面は、本物の業務画面として作っている**。ヘッダーの「ダミー画面」の表示は、外部サービスの代わりのGMOサインだけ（2026-11-18）。ほかの画面は、本番でもそのまま使える見た目・文言・操作を意図している。
- **モックで実装していない要件**は、[今後の要件](../FUTURE_REQUIREMENTS.md)に、区分つきで記録してある。**【正式版の要件（モックでは実装しない）】は、正式版では必ず実装する**（例: 情報の公開範囲 R-1）。「モックにないから不要」ではない。

## 設計の原則（判断が分かれたときの拠りどころ）

1. **業務を止めない・漏らさない**: 電話の聞き忘れ、前日確認のかけ忘れ、入力漏れを、画面で防ぐ（聞き取り状況の表示、前日確認の未連絡の絞り込み、希望連絡時間帯順、経費精算の指摘）。便利さより、**漏れの防止**を優先する。
2. **判断する画面で、判断の材料が見える**: 配車係が誰を当てるかを決めるなら、その画面で、お客様のランク・性別・鑑定士のランク・移動距離が見える。別の画面へ行かないと分からない、は避ける（2.3 配車確定）。
3. **決める人と、実行する人を分ける**: オペレーターは**仮確定**まで、**確定は配車係**。鑑定士の名前は、お客様に伝えない。経費の一次チェックは営業サポート。権限の線引きを、画面で崩さない（[用語集](glossary.md)・各機能の仕様）。
4. **要件の記録と、モックでの実装は、別**: 仕様として残すことと、モックで作ることは、別の観点（上の区分）。**区分が読み取れないときは、実装せず、設計者に確認する**。
5. **決めていないことは、決めない**: 迷う点・矛盾は、実装せずに、設計者に確認する。保留は、保留として記録する（[保留中の要件](../FUTURE_REQUIREMENTS.md)）。
6. **機能は、独立させる**: 機能別に、仕様・（将来は）データ・APIを分け、**機能どうしは、APIとIDだけでつなぐ**。文書も、機能別（`docs/features/`）。

## 画面設計の方針（設計者が、画面のレビューで示してきたこと）

エンジニアが、**新しい画面・変更を作るときも、同じ方針で**作ってほしい。

1. **同じ意味を、2か所に書かない（冗長にしない）**。実線／点線で表している状態を、さらに文字でも書かない。休みの人の名前の下は「0件」にして、「休み」を近くに2か所書かない。**補足説明は、「?」アイコンにまとめる**（[画面共通のルール](ui-rules.md)）。
2. **状態は、色以外（枠線など）で表し、色は意味のあるものに使う**。確定／仮確定は、実線／点線／二重線。色は、ランク（SS＝赤・S＝橙・A＝緑・B＝青）や、鑑定士の区別に。**同じ意味は、画面をまたいでも、同じ色**（鑑定士と顧客のランクは、同じ色）。色が増えすぎないよう、基本は4色（例外は、ui-rules に明記）。
3. **カレンダーの枠を押したら、右側に詳細が出る**。**右側のエリアは、はじめから確保**する（出たときに、カレンダーが縮まない）。**判断に要るときは、登録内容を、すべて出す**。
4. **開閉・操作の見た目を、そろえる**。開閉は「▼ 開く／▲ 閉じる」で、ボタンの位置は、右上に固定。**性質の違う操作を、混ぜない**（受付の変更・取消と、前日確認の記録は、別の置き場所）。
5. **見せ方が崩れない**。バッジなどが付いても、文字が折り返して崩れない（メニューのバッジは、項目の下に並べる）。
6. **押せるものは、操作できる**。カレンダーの枠が押せるなら、その予定の編集・前日確認もできる（元からの予定も、押すと受付として取り込む）。「押せるが何もできない」は、避ける。
7. **言葉は、用語集にそろえる**。使わない語を、画面に出さない。同じ意味は、1つの語に統一する（例: 「欠勤」「午前休」「午後半休」は、すべて「休み」）。
8. **本物の業務画面らしく**: ヘッダーの「ダミー画面」の表示は、GMOサインだけ。デモ専用のボタンは、本番で消えるとはっきり分かる見た目（「デモ｜」）にする。
9. **絵文字は使わない**（線画のアイコンと、文字として表示される記号だけ）。
10. **全画面に、画面IDを振る**（クライアントからの修正依頼で、どの画面かを伝えるため。[画面ID一覧](../SCREEN_IDS.md)）。画面・モーダルを足したら、IDも足す。

- **詳細パネルは、項目を並べず、意味ごとの枠（見出しつき）に分ける**（2026-11-18）: 項目が多い詳細（訪問・予約）は、「訪問」「お客様」「売りたいもの」「当日の状況」「受付の記録」のように、読む人が探しやすいまとまりにする。値のない項目・空の枠は出さない。

- **機能が複数ある業務画面は、開閉式の左メニュー（☰）で切り替える**（2026-11-19）: 経理部・倉庫・タブレットなどと同じ見た目にそろえる。査定部も、機能が増えるため、同じ左メニューにした（鑑定士サポート／査定）。ヘッダーに「部署名 › 機能名」を出す。

- **配車係には、誰を当てるかの判断の材料を、できるだけ開示する**（2026-11-19）: 配車係は、誰が行けば最も効果的かを差配する立場。顧客ランク・性別・鑑定士のランクに加え、**売りたいものに貴金属があるか**も、帯の印で見せる（1円でも高く買い取るため、上顧客・貴金属は、ランクの高い鑑定士を当てたい。[配車確定 2.3](../features/dispatch/spec.md)）。印は材料で、配車は縛らない。

## 守ってほしい業務上の前提

詳細は、各機能の仕様の**太字**の記述が正。特に、次は、崩さない。

- **オペレーターは仮確定まで。確定は配車係が、主に翌々日分を毎日。確定した訪問だけが、鑑定士の予定に出る**（[配車確定](../features/dispatch/spec.md)、[受付](../features/callcenter-intake/spec.md)）。
- **売上のため、高いランクのお客様には、高いランクの鑑定士を当てる**。**お客様の男女比**も、配車で重視する（女性のお客様は客単価が高い）。顧客ランクは、新規かリピーターかとは別。**ランクは、変わっていくもの**（変遷を残す。鑑定士のランクも、顧客ランクも）。
- **クーリングオフ**: 訪問買取の商品は、買取から10日間、販売せず保管。依頼を作るのはコールセンター、返送・完了は倉庫。**店頭買取は、対象外**（[クーリングオフ](../features/warehouse-cooloff/spec.md)、[店舗](../features/store-purchase/spec.md)）。
- **所持金（財布）は1つ**。補充金は、鑑定士が引き出すまで所持金に入らない（[経費](../features/tablet-workday-expense/spec.md)）。
- **他の鑑定士の情報を、鑑定士に見せない**（正式版の要件。ただし、ランク・厄介度・クーリングオフ歴・リピーターは見せてよい。見送り品は見せない）。画面で隠すだけでなく、**サーバーが、返すデータから除く**（[今後の要件 R-1](../FUTURE_REQUIREMENTS.md)）。
- **高額品（紫・赤のシール）は、専門の査定員が確認して確定する**（2026-11-19）。郵送で届いた商品のシールのQRを読み取り、鑑定士が登録した内容を確認して確定する。**買取金額は、お客様に支払い済みなので、査定では変えない**（[査定部 3.2](../features/appraisal-hq/spec.md)）。**鑑定士（責任者）は自分で確定でき、鑑定士（一般）の登録は査定部の確認が要る**（モックでは区別せず、正式版の要件。[R-5](../FUTURE_REQUIREMENTS.md)）。
- **電話の履歴は、オペレーターを含む他の人にも見せる**（他の鑑定士の名前は伏せる。[R-2](../FUTURE_REQUIREMENTS.md)）。

## エンジニア（とAI）が、開発を始めるときに

- **まず読む順番**: [INDEX.md](../INDEX.md) → この文書 → [用語集](glossary.md) → 触る機能の `spec.md` → [今後の要件](../FUTURE_REQUIREMENTS.md)。**全部は読まなくてよい**（機能別に分けてあるのは、そのため）。
- **モックのコードは、仕様を確かめるための参考**。正式版は、構成を作り直してよい（モックは、localStorage・ダミーデータ・CDN読み込み。[本実装に向けた課題](production-gaps.md)）。**振る舞い（画面・業務ルール）は、モックと、仕様書に合わせる**。
- **テスト（`tests/`、約680件）は、振る舞いの正**。ロジックは、画面から独立した純関数にして、テストを先に書く（[開発ルール](development.md)）。移行するときも、テストを、仕様の確認に使える。
- **AIに任せるとき**: 機能ごとの `spec.md` を読ませ、**仕様と矛盾する場合は、実装せずに確認させる**。用語集の「使わない語」を、画面・コメントに入れさせない。区分が不明な要件は、実装させない。
- **仕様を変えたら、その機能の `spec.md` を、同じ作業で更新する**（コードだけ変えない）。食い違いを見つけたら、設計者に知らせる。
- **設計者に確認すること**: 業務の判断（誰が決めるか、誰に見せるか）、仕様の矛盾、区分が読み取れない要件。**技術の選択（言語・DB・構成）は、エンジニアが決めてよい**。

## この文書への追記のルール

- 設計者が、**設計の考え方・判断の原則・画面の方針**を指示したら、該当する節に**日付つき**で足す（例: 「（2026-11-18）」）。矛盾する方針は、古いほうを消さず、「変更（日付）」と書いて残す。
- **業務の取り決め（誰が何をするか）**は、機能の `spec.md` に書く。**今は作らない要件**は、[今後の要件](../FUTURE_REQUIREMENTS.md)に、区分つきで書く。この文書には、**それらをまたぐ考え方**だけを書く。
- Claude Code は、設計者から方針の指示を受けたら、**この文書に追記する**（CLAUDE.md に、その旨を書いてある）。
