## 10. 本実装に向けた課題（モックでは未対応）

> **正式版の要件として記録しておくもの**（モックでは実装しないが、正式版では必ず実装する）は、[FUTURE_REQUIREMENTS.md](../../docs/FUTURE_REQUIREMENTS.md) に、**区分（モックで実装／正式版の要件／未定／保留）つき**で書く。この章は、モックの限界（認証・サーバー・外部サービスなど）の一覧。

- **録音**: モックは録音データを、その端末のブラウザ（IndexedDB）にだけ置く（別の端末・本社からは聞けない）。本実装では、サーバーへのアップロード（分割送信・再送）、保存期間、聞ける人の権限、画面ロック・通話・アプリ切替で録音が止まる問題（ネイティブアプリ化も含めて検討）、録音を断られたお客様の扱い（いまは了承のチェックが必須）が課題。

- 認証・認可（現状は何でも通る）。倉庫・本社・配車係・オペレーターの権限分離。マスタ管理を使える人（管理者）の役割、パスワード、変更履歴。
- 鑑定士を、マスタ管理の社員の名簿につなぐ（7章）。営業所マスタを、エリア判定・配車・鑑定士の所属につなぐ。配車係・経理担当が操作した記録に、社員を結びつける。
- 用語集の「予約」→「受付」など、画面の文言・コードに残る古い言い方の置き換え。
- localStorage → サーバーとDB。画面間連携は、現状の「同一ブラウザ内の共有」から、APIとリアルタイム通知へ。
- 音声認識・AI査定・レシートOCR・実カメラのQR読取、GMOサインの実API連携、配送業者の取込CSV形式への適合。
- 手数料率・鑑定士のランク・エリア境界・クーリングオフ保管日数（10日）など、運用で決まる値の確定。
- **店舗（11章）の未対応**: レジ現金（始業・終業の現金照合・前日繰越金・経理部への反映。鑑定士の現金管理と同じ形にする予定）、査定部への査定依頼・承認（店頭買取は、いまはスタッフが金額を入力するだけ）、経理部の店舗での絞り込み・店頭買取の現金の帳簿への反映、業績の店舗別の集計、店舗の営業時間と来店予約の時刻の連動、納入先の倉庫への連動、古物台帳（買取の記録の帳簿）と、契約書への古物商許可番号の印字。
- **店頭用の契約書の様式**: GMOサインの契約書（`gmosign/contractForm.js`）は、訪問買取の様式のままで、クーリング・オフの記載がある。店頭買取は対象外なので、様式を分ける必要がある（法務の確認が要る）。説明事項の「対象外であること」の文言（`src/storePurchase.js`）も、法務の確認が要る。
