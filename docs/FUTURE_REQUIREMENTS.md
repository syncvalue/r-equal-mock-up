# 今後の要件（未実装・本実装に向けて）

**今は改修しないが、今後、機能を実装・変更するときに守る要件**を、依頼を受けるたびに足していく。
（現在の仕様は、機能別の `docs/features/*/spec.md` と `docs/shared/`（入口は `INDEX.md`）。ここは、まだコードに反映していない約束ごと。実装したら、該当する機能の `spec.md` に仕様として移し、この項目に「実装済み（日付）」と書く。）

**区分（各項目の見出しの下に付ける）**: 仕様として残すことと、モックで実装することは、別。**モックでは実装しないが、正式版を作るときに忘れないよう、要件として記録する**ものがある。
- 【モックで実装】: モックの画面・データで実装する（実装したら、該当する機能の `spec.md` に移す）。
- 【正式版の要件（モックでは実装しない）】: モックでは作らない。**正式版を作るときに、必ず実装する要件**として記録する（モックでは、認証・サーバーがないため、作れない・作る意味が薄いもの、など）。
- 【未定】: モックで実装するか、正式版だけにするか、まだ決めていない（依頼者に確認する）。
- 【保留】: 要件そのものを、のちのち詰める。

使い方:
- 新しい機能を実装するとき、関係する項目がないか、先にここを読む。
- 項目と、いまのモックの動きが食い違うところは「いまのモックとの差」に書いてある。実装のときは、そこを直す。
- 項目は、追加した日付を添える。

## R-1 情報の公開範囲: 鑑定士に、他の鑑定士の情報を見せない（2026-11-17）

**区分: 【正式版の要件（モックでは実装しない）】**（モックは、ログイン中の鑑定士の区別がデータの取り出しに入っておらず、認証・認可がない（[production-gaps.md](shared/production-gaps.md)＝仕様書10章）ため。モックで見せ方だけ先に作るかは、依頼があれば決める）

**要件**
- 鑑定士には、**他の鑑定士の情報を見せない**。
- 例: お客様Aさんに、X鑑定士が1回目、Y鑑定士が2回目の訪問をした場合、**Y鑑定士には、X鑑定士の訪問履歴は見えない**。
- **お客様Aさんの基本情報は、Y鑑定士にも見せてよい**（氏名・連絡先・住所・ランクなど、お客様そのものの情報）。

**見せない（他の鑑定士の）もの**
- 他の鑑定士が行った訪問の履歴（日時・買取内容・金額・結果・見送り品・メモ・経費など）。
- 他の鑑定士が付けた、お客様の評価・メモ。
- 他の鑑定士の名前（「前回の担当」など、誰が訪問したかが分かる表示）。

**見せてよいもの**
- お客様の基本情報（氏名・フリガナ・電話番号・住所・生年月日など）。
- 自分が担当した訪問・買取の履歴と、自分が付けた評価。

**決定（2026-11-18 に依頼者が決定）**
- **他の鑑定士にも、見せてよい**: お客様の**ランク・厄介度・クーリングオフ歴**（お客様の基本情報として）。**リピーターであること（何回目の訪問か）**。
- **他の鑑定士には、見せない**: お客様の**見送り品**（他の鑑定士の訪問の結果。上の「見せない」に含む）。
- **業績ダッシュボードの、グループリーダーがグループ全員を見られる**（[tablet-dashboard](features/tablet-dashboard/spec.md)＝仕様書1.4）は、この要件の**例外として残す**。
- **配車係・コールセンター・査定部・経理部など、鑑定士以外の部署の見え方は、この要件の対象外**（これまでどおり）。
- 本実装では、画面で隠すだけでなく、**サーバー側で、ログイン中の鑑定士に返すデータから、他の鑑定士の分を除く**こと（画面で隠しても、データに含まれていれば見えてしまうため）。

**いまのモックとの差（実装のときに直す）**
- 鑑定士タブレットの「お客様確認」（[tablet-visit](features/tablet-visit/spec.md)＝仕様書1.6 の1）は、リピーターの**過去の買取履歴・評価**を、担当に関係なく出している（`src/customerHistory.js`・`src/customerHistoryView.js`・`src/customerProfileView.js`）。同じく、「これまでに担当した鑑定士」（`staff`）も出している。
- 「今日の予定」の訪問結果、**お客様の見送り品の表示**も、担当を区別していない（見送り品は、他の鑑定士には見せない。上の決定）。
- モックは、ログイン中の鑑定士の区別がデータの取り出しに入っていない（認証・認可は、[仕様書10章](shared/production-gaps.md)のとおり未対応）。

## R-2 電話の履歴は、オペレーターを含む他の人にも見せる（2026-11-17。顧客検索で実装済み）

**区分: 【モックで実装】済み（顧客検索・受電履歴）。ただし、下の「配車係・査定部にも見せる」は【未定】**（モックで画面に出すか、正式版だけにするかを、依頼者に確認する）

**要件**: お客様から見れば、鑑定士がかけてもオペレーターがかけても、「電話がかかってきた」ことに変わりはない。しつこいと思われないよう、**電話の履歴は、オペレーターを含む他の人にも見えるようにする**。
- 実装済み: 鑑定士の電話の記録（`src/callLog.js`）を、コールセンターの受電履歴に出す。前日確認の電話も、鑑定士の画面の履歴に出す（[tablet-customer-search](features/tablet-customer-search/spec.md)＝仕様書1.9）。
- **R-1（他の鑑定士の情報を見せない）との関係**: 電話の履歴は共有する。ただし、**ほかの鑑定士の名前は伏せる**（訪問履歴ではなく「電話をしたという事実」だけを共有するため）。**この線引きでよい**（2026-11-18 決定）。
- **決定（2026-11-18）**: **受電履歴は、配車係・査定部にも見せる**。
- 未対応: 受電履歴を、配車係・査定部の画面に出すこと（いまは、コールセンターの受電画面だけ）。電話の記録のサーバー共有。

## R-3 ランクは変わっていくもの（鑑定士・顧客とも）。新規のお客様にも顧客ランクを付ける（2026-11-18）

**区分: 【モックで実装】済み**（受付の欄・鑑定士ランクの変更と変遷・前日確認のメモの共有）

**要件**
- **顧客ランクは、新規かリピーターかとは別の軸**。**新規のお客様にも、顧客ランクを設定する**（買取の実績がなくても、住所から高級住宅街と分かる場合は、SSと推測する、など）。
- **鑑定士のランクも、顧客ランクも、変わっていく**。変遷（いつ・どのランクから・どのランクへ・誰が）を残す。

**実装済み（2026-11-18）**
- 顧客ランクと「新規／再訪」は、別々の札で出す（配車確定の帯・お客様の詳細）。新規のお客様にも、ランクを登録できる（配車係の「お客様の評価を登録・変更する」）。
- 顧客ランクの**変遷**は、お客様の評価を登録するたびに足す（`src/customerEval.js` の `rankHistory`）。お客様の詳細に「ランクの変遷」を出す。
- 受付した訪問に、受付で付けたランク（`customerRank`）を持てる（ダミーのお客様・取り込んだ予定が使う）。登録・買取の実績から決まるランクがあれば、そちらを優先する。

**実装済み（2026-11-18。依頼者が決めた内容）**
- **受付（オペレーター）の画面に、新規のお客様の顧客ランクを入れる欄**（「顧客ランク（推測）」。住所や話し方から推測して SS〜B を入れる。任意）。受付の記録の `customerRank` に残る。**配車係が、あとから直せる**（お客様の評価の登録。登録・買取の実績から決まるランクがあれば、そちらを優先）。住所からの自動推測は、しない。
- **鑑定士のランクは、マスタ管理の社員の画面で変更する**（鑑定士の行の「ランクを変更」）。変更のたびに、ランク・日付・誰が、を残し、一覧に「ランクの変遷」を出す（`src/staffRank.js`）。
- **前日確認の記録（連絡の結果・日時・メモ）は、鑑定士タブレットの予定の詳細に出す**（読むだけ。受電時のヒアリングのモーダルにも出る）。
- **前日確認の連絡の期限は、設けない**（前日であればいつでもよい）。

## R-4 アクターの区分（一般・責任者）と、役員・社長・システム管理者の追加（2026-11-19）

【正式版の要件（モックでは実装しない）】

- 役割に**区分（一般・責任者）**を持たせる。対象は、鑑定士・オペレーター・配車係・査定員・経理担当・倉庫担当・店舗スタッフ（**区分を持たない役割があれば、設計者が指示する**）。
- **役員・社長・システム管理者**を、役割として追加する（**区分はない**）。システム管理者は、マスタ管理を使う人。役員・社長は、閲覧のみ（仮）。
- **確認が要ること**: 責任者にだけできること（承認・業績の閲覧範囲・社員の管理など）。鑑定士の責任者＝グループリーダーか。役員・社長に見せる範囲。システム管理者が、業務の画面を見られるか。
- 使える機能の一覧（○△×）は [actors.md](shared/actors.md) の「機能の使い分け」（責任者・役員・社長・システム管理者の行は仮）。
- **いまのモックとの差**: 役割は7つ（`src/employees.js` の `ROLES`）で、区分はない。ログインしても、権限の分離はない（[production-gaps](shared/production-gaps.md)）。

## R-5 査定の確定の流れは、鑑定士の区分で変わる（2026-11-19）

【正式版の要件（モックでは実装しない）】（モックには、鑑定士の区分（責任者・一般）がない。R-4）

- 紫・赤のシールの商品（高額品）は、専門の査定員でないと査定できない。その確定の流れが、**登録した鑑定士の区分**で変わる。
  - **鑑定士（責任者）**: 登録時に、**自分の権限で確定まで進められる**（査定部の確認は要らない）。
  - **鑑定士（一般）**: 登録時は**未確定**。のちに、**査定部（査定員）が確認して、確定済みにする**（査定部「査定」。[3.2](features/appraisal-hq/spec.md)）。
- 責任者を鑑定士のどの範囲にするか（グループリーダーと同じか）は、R-4 の確認事項のまま。
- **いまのモックとの差**: 区分の違いは扱わず、**紫・赤の商品は、すべて査定待ち**として、査定部に出す（`src/unitAppraisal.js` の `appraisalStatus`）。実装のときは、登録時に「責任者が登録した商品は、確定済み（登録者が確定）で作る」ようにし、確定した人（登録した鑑定士か査定員か）を区別して残す。
- 確定の結果を、鑑定士のタブレット・買取明細・倉庫の商品に反映することも、正式版で行う（モックは、商品（入庫の記録）にだけ残す）。

## R-6 マーケティング部: 反響の測り方と、チラシの作成の扱い（2026-11-19）

**区分: 【未定】**（モックで実装するか、正式版だけにするか、依頼者に確認する）

マーケティング部（[12章](features/marketing-flyers/spec.md)）は、チラシの登録・反響管理・オペレーターへの「今日配布のチラシ」まで、モックで実装済み。次は、まだ決めていない。
- **反響を、買取の金額・粗利で測る**: いまは、受付の件数・反響率・1件あたりの費用まで。「どのチラシが、いくら稼いだか」は、受付→訪問→買取（契約・粗利）をたどる必要がある。
- **配布エリアと、受付の住所のひもづけ**: いまの配布エリアは、文字の自由入力。都道府県・市区町村のマスタにして、エリア別の反響・オペレーターへの見込みを出すか。
- **チラシそのもの（デザイン・画像・PDF）の作成・保存**: 業務は「チラシの作成」だが、いまは、配布の記録の登録まで。制作の進み具合・データの保管を、このシステムで扱うか。
- **オペレーターへの見せ方**: いまは、今日配布の分だけ。「明日の配布予定」「過去のチラシの反響の傾向（曜日・エリア別）」も見せるか。
- **マーケティング担当の責任者**（R-4）にだけできること。

## R-7 店舗のお客様画面: 端末のひもづけと認証（2026-11-19）

**区分: 【正式版の要件（モックでは実装しない）】**

店舗のお客様画面（[11.6](features/store-purchase/spec.md)）は、モックでは、**同じブラウザの保存（localStorage）で、ウィンドウどうしをつないでいる**。正式版では、次を守る。
- **店舗スタッフの端末と、お客様画面の端末を、サーバー経由でひもづける**（店舗ごと・席（カウンター）ごと。別の端末・別のOSでも連動する）。
- **お客様画面は、店舗に置いた端末だけが開ける**（登録した端末のみ。URLを知っていても、外から見られない）。お客様の氏名・住所・生年月日が出る画面のため。
- **お客様画面に出す内容は、サーバーが、お客様に見せてよい項目だけを返す**（画面で隠すだけにしない。顧客ランク・厄介度・見送り品・シールNo.などを含めない）。
- 来店の一覧へ戻る・見送り・ログアウトで待機の画面に戻す動きは、サーバー側でも保証する（端末が落ちていても、情報を残さない）。

## 保留中の要件（2026-11-18 に、依頼者が「一旦保留。のちのち要件を詰める」と決めたもの）

**区分: 【保留】**（モックで実装するか、正式版だけか、も含めて、のちのち決める）

- **経費精算**: 営業サポートの一次チェックのあと（経理担当による二次チェック、帳簿への反映）。
- **店舗（店頭買取）**: レジ現金の管理、査定部との連動、業績の店舗別の集計、営業時間と来店予約の時刻の連動、納入先の倉庫への連動、古物台帳、店頭用の契約書の様式と説明文（法務の確認が要る）。
- **配車確定**: 過去の日付を、その日のランクで出すか、現在のランクで出すか（いまは、現在のランク）。
- **訪問カレンダー**: 背景の濃さの区切り（いまは、割合に比例して連続的に濃くしている）。
