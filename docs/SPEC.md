# 出張買取アプリ（モックアップ）機能仕様書

このリポジトリを引き継ぐ方向けに、これまでの依頼内容を機能ごとに整理した仕様書です。
**「なぜそうしているか」（業務上の前提・決定の経緯）を中心に**まとめています。コードを読めば分かることは省き、迷いやすい点を残しています。

- 記録日: 2026-10-25（git履歴 2026-10-21〜10-25 の127コミットと、依頼時のやり取りから整理）。同日、**マスタ管理（7章）と用語集**、**出張（7.4）**、**店舗（店頭買取。7.7・11章）**を追加。
- **表記は、次の「用語集」にそろえる**。画面の文言・仕様・コードのコメントを書くときは、先に用語集を見てください。
- 現状: **モックアップ**です。外部サービス・サーバーはなく、すべて localStorage とダミーデータで動きます。
- 関連資料: 画面の使い方の詳細は [README.md](../README.md)（特に「倉庫・物流」の節が詳しい）。振る舞いの正は `tests/` のテスト（`npm test`、418件、全件成功を確認済み）。
- 本書とコードが食い違ったときは、**テストとコードが正**です。仕様を変えたら本書も更新してください。

## 用語集（表記の統一）

同じものを指す言葉が画面や資料でバラバラにならないよう、**使う語**を決めています。「使わない語」を見つけたら直し、新しい語を足すときは、先にここに載せてください。

### 会社・部署・社員・役割

| 使う語 | 意味 | 使わない語・注意 |
|---|---|---|
| **会社** | クライアントの「REqual」**1社だけ**。複数の会社は持たない（部署は、すべてこの会社に属する） | |
| **部署** | 会社の中の組織の単位（営業部・コールセンター・査定部・経理部・物流部など）。**並べるだけで、階層（課・チーム）はない** | 「所属」だけで部署を指さない（所属＝社員が部署・倉庫に属すること） |
| **社員** | このシステムを使う**社内の人**。**いずれかの部署に属し**、1人にひとつの**役割**を持つ。マスタ管理（7章）の社員で登録する | **ユーザー**（以前の呼び方）、スタッフ。お客様は含まない。**コードの `USERS`・`userId`（`src/dashboard.js` など）は営業だけを指す古い名前**で、社員全体の名簿は `src/employees.js` |
| **役割** | 社員のシステムでの立場。営業・オペレーター・配車係・査定員・経理担当・倉庫担当・店舗スタッフの7つ。**役割で、使う画面が決まる。部署とは別の項目**（例: コールセンターの部署に、オペレーターと配車係がいる） | ロール（権限の細かい設定は、本実装の課題） |
| **営業** | お客様の自宅へ行き、現地で買取をする人。営業タブレットを使う | 営業マン、営業員、営業担当、担当者 |
| **グループリーダー** | 営業のうち、グループ全員の業績を見られる人（役割ではなく、営業の属性） | 「リーダー」と略さない |
| **担当営業** | 受付・訪問ごとに割り当てた営業。**お客様には名前を伝えない** | 営業担当 |
| **オペレーター** | コールセンターで電話を受け、**仮確定まで**行う人 | オペレータ、受付者、受付担当 |
| **配車係** | 仮確定された訪問を**最終確定**し、営業の割り当てを調整する人 | 配車担当 |
| **査定員** | 査定部の人。営業の査定依頼に回答し、買取を承認する | 査定担当、査定部の担当者 |
| **査定依頼** | 営業が、商品の査定を査定部に頼むこと（**任意**）。商品ごとに、営業と査定員の**チャット**（やり取り）が続き、査定員が**完結**する。状態は、依頼中（査定員の返信待ち）・回答済み（営業の返信待ち）・完結 | 本社査定、本社への査定依頼 |
| **完結** | 査定員が、査定依頼のやり取りを終えること。**商品の承認の条件**（査定依頼があるとき）。完結のあとに、どちらかが話すと再開する | 完了（クーリング・オフの完了などと区別） |
| **経理担当** | 経理部の人。現金・入金・経費を扱う | 経理部の担当者 |
| **倉庫担当** | 倉庫・物流の画面を使う人。いずれかの倉庫に所属する。**本社に所属する人も倉庫担当** | 担当者（単独）、倉庫の担当者、本社担当、スタッフ |
| **店舗スタッフ** | 店舗の画面を使い、**来店したお客様の受付と、店頭買取**をする人。いずれかの店舗に所属する。営業と違い、お客様の自宅へは行かない | 店員、店舗担当、販売員（買取が仕事なので）、営業（営業は訪問する人） |

- **「担当者」は単独で使わない**。人を指すときは、必ず役割名（営業・オペレーター・査定員・倉庫担当…）で書く。
- 受付を取ったオペレーターの項目名は「オペレーター」（以前の「受付者」は使わない）。

### 0.2 業務の流れ（全体）

```
お客様の電話
  → [コールセンター] 聞き取り・エリア判定・担当営業の仮決定 ＝ 仮確定（オペレーター）
  → [配車確定] 配車係が翌々日分などを確定
  → [営業タブレット] 予定に出る → 始業 → 訪問 → 現地買取 → 訪問終了
        ├ 査定は [査定部] が承認・助言
        └ 契約書は [GMOサイン] で印刷し、紙で署名
  → 持ち帰り（入庫）→ [倉庫・物流] 保管（10日間はクーリングオフ期間）
  → 出品・委託・直接販売 → 購入者・業者へ発送 → 売上・利益の管理
  → （クーリングオフ）お客様の電話 → [コールセンター] 依頼を作成 → [倉庫] 回答・返送 → 返金の確認で完了
  → 終業・日報 → [経理部] で現金・経費を確認

お客様の来店予約（電話）→ [コールセンター] 店舗と日時を受け付ける（来店予約。仮確定・配車はない）
お客様の来店（予約あり・飛び込み）→ [店舗] 受付 → お客様確認・説明・査定・シール・契約書・代金のお支払い ＝ 店頭買取
  → 入庫待ち → [倉庫・物流] 入庫（買取のその日から出品できる。10日間の保管期間はない）
```

### 0.3 技術と構成

- Vite + vanilla JS（フレームワークなし）+ Tailwind CSS（CDN。**ネット接続が必要**）。
- 画面間の連携は、同一ブラウザの localStorage を介します（別タブで開いて確認）。キーは `src/store.js` に集約。
- ロジックは画面から独立した純関数にして `src/` に置き、`tests/` で検証しています。画面は各ディレクトリ（`callcenter/`・`honsha/`・`accounting/`・`warehouse/`・`master/`・`store/`・`gmosign/`・`tablet/`）。
- 各画面下部の「（デモ用）データ初期化」で、マスタ以外を消せます。マスタ管理のデータ（社員・部署・営業所・出張・店舗・倉庫・委託先。7章）は消えません。
- 起動は `docker compose up --build`（http://localhost:5173）。Docker を使わない場合は `npm install` のあと、`package.json` の dev スクリプトで開発サーバーを起動。テストは `npm test`。

### 0.3.1 補足説明は「?」にまとめる（画面共通）

- **画面に常時出す文字は、値・ラベル・状態・警告に絞る**。操作の手順・仕組み・理由・注記などの補足説明は、見出しやラベルの横の「?」アイコンにまとめ、**押す（タップする）と吹き出しで表示**する。見たい人だけ押せばよく、慣れた人の邪魔にならない。
- 吹き出しは、もう一度「?」を押す・ほかの場所を押す・Escキー・スクロールで閉じる。画面の端ではみ出さないよう位置を寄せる。
- **「?」にしないもの**: エラー・警告・取り返しのつかない操作の確認、短い空状態（「ありません」）、入力を促す短い指示、お客様に読み上げる・見せる必要がある文言（クーリング・オフの説明事項など）、印刷物の本文。
- 実装は `src/help.js`（`helpIcon(text)` と、各画面の起動時に呼ぶ `initHelp()`）。新しい補足説明を足すときも、本文に書かず `helpIcon` を使う。

## 1. 営業タブレット（`/tablet/`）

### 1.1 ログイン

- ID・パスワード → SMS認証コード（2要素認証）。パスワード再設定もSMSコードで本人確認する。
- コードは6桁・有効5分・再送は30秒待ち・入力ミスは3回まで（`src/auth.js`）。
- パスワード条件: 8文字以上・英字と数字を含む・IDと同じ不可。
- 存在しないIDでも、画面上は同じように進める（ID有無を知られないため）。
- モックのため、IDは何でも可。既存IDならその営業、それ以外は先頭の営業（鈴木 一郎）としてログイン（デモ用アカウントは `sales01`〜）。
- **初期画面は状態で切り替わる**: 未ログイン→ログイン、始業前→始業、始業済み→ダッシュボード。データ初期化でログイン状態も破棄。

### 1.2 メインメニュー（左の開閉式ドロワー）

ダッシュボード／始業／今日の予定／現地買取／経費管理／商品の持ち帰り／終業・日報。
始業と終業・日報は別項目で、状況に応じて活性・非活性が切り替わる。

### 1.3 始業・終業と経費（`src/workday.js`）

**重要な決定**: 始業するまで**現地買取だけ**が使えない。他の機能は始業前・終業後も使える。

- **始業**: 前日繰越金を実際に数えて照合（**ずれがあれば理由が必須**）→ 点検8項目（飲酒・体調・身だしなみ・社員証・車両・タブレット・買取用資材・本社からのお知らせ）をすべてチェック → 記録して業務開始。
- **所持金** ＝ 前日繰越金 ＋ 本社からの入金 − 経費。毎朝の定例入金（30万円）はダミー。繰越金の初期値は5万円。
  - **未始業の営業にも、前日繰越金は手元にある**ものとして扱う（経理部の画面でも同様）。
- **経費**: 種別（ガソリン代・昼食代・備品購入・高速/駐車場・交通費・その他）＋金額＋レシート写真。レシートはAIで読み取り、種別・金額・内容を自動入力（人が確認・修正できる前提。撮影が先頭）。数字は右詰め。
- **買取代金は、訪問終了時に経費として自動計上**される（所持金から減る）。経費の集計・「高額」判定からは除外される。
- **終業**: 帳簿残高と実際の現金を照合（ずれは理由必須）→ 終業点検4項目 → 日報提出。日報には現金収支・経費内訳・訪問と買取の実績が自動集計される。**終業後は、現地買取と経費の計上ができない**。翌日の繰越金は、終業時に数えた金額。
- **訪問できなかった場合**: 不在／日程変更の依頼／お客様都合のキャンセル／その他（その他はメモ必須）。**訪問実績には数えるが、営業の責任ではないため業績（成約率など）に影響しない**。日報・本社画面に反映される。

### 1.4 ダッシュボード・メッセージ・業績

- 本社からのメッセージとグループリーダーからのメッセージを、別枠・開閉式で表示。枠は2件分の高さに固定し、詳細はモーダル。「他○件あります」を表示。重要フラグ・既読管理あり。宛先は「全員」または「グループ」。
- **業績ダッシュボード**: 今日／今週／今月。訪問数・契約数・買取額・成約率・平均単価。月間目標に対する進捗とペース。
  - **閲覧権限**: 一般は自分のみ。**グループリーダーはグループ全員・メンバー個別も閲覧可**（デモ用にロール切替あり）。
  - 訪問ごとの結果モーダル、期間中の日報の閲覧（リーダーはメンバーの日報も）。
  - 業績データはすべて、営業×日付から決まる疑似乱数のダミー（日曜と未来日は休み扱い）。
- グループは A（東日本）/ B（西日本）、営業は16名（`src/dashboard.js`）。

### 1.5 今日の予定・ルート確認

- **前日（実績）・今日・明日の3日表示**（明後日は非表示）。未訪問・訪問中・完了を色とバッジで区別。訪問済みをタップすると結果の詳細。
- ルート確認は予定画面に統合。2件目以降の出発地は「前の予定の場所／現在地」で切り替え。
- 予定の詳細・訪問開始画面で、**受電時のヒアリング**（コールセンターの入力内容）と、**お客様のランク・厄介度・クーリングオフ歴・見送り品**を確認できる。
- コールセンターで**確定**した予約だけが予定に出る（仮確定は出ない）。

### 1.6 現地買取の流れ（`src/views.js` の `STEPS`）

訪問開始 → お客様確認 → 説明事項 → 買取明細 → 買取商品の確認 → シール紐づけ → 送信・終了

1. **お客様確認**: 初めて／リピーター（何回目）を表示。リピーターは過去の買取履歴・評価を確認できる。
2. **説明事項**（査定前に必須）: 5項目（買取の流れ・断れること・撮影と写真送信の了承・本人確認の必要性（古物営業法）・クーリング・オフ）を説明してチェックし、**他商品を提案してよいか**をお客様に確認する。両方済むまで次へ進めない。
3. **買取明細**: 商品マスタから選択／AIカメラ／査定部への査定依頼／AI査定。金額は通貨形式（¥・円・3桁区切り）。明細の段階でもシールを貼りながら進められる。
   - 査定依頼（任意）は、商品ごとの**チャット**。最初の依頼は、状態・補足の文章か写真のどちらかがあればよい（**写真は任意**）。査定員の返信（コメント・提案額）に、営業が続けて返信できる（文章または写真）。1回で終わらなくてよい。査定員の返信が未読の商品には❗が出る。提案額は、返信ごとの「買取金額に反映」で取り込む。
   - 明細の行には、査定依頼の状態（査定中・返信あり・査定完結）が出る。
4. **買取商品の確認**: **お客様に見せる画面**（文字は大きめ）。承認済みと確認中を一目で区別。**査定部の承認が必要**。承認後に金額・ランク・数量が変わったら、再承認が必要（`stale`）。**査定依頼を出した商品は、その査定依頼が完結するまで承認されない**（依頼がない商品は関係なし）。
5. **シール紐づけ**: 商品1点（数量があれば1個ずつ）にシールのQRを読み取って紐づける（カメラ起動はモック）。**シールの色（紫・赤・黄・緑・青）は、QRを読み取ると自動で選ばれる**（シールNo.の「RQ-」の次の1文字が色: P紫・R赤・Y黄・G緑・B青。QRから分からない古いシール・手入力のときは、画面で色を選ぶ。色が決まらないと次へ進めない）。黄・緑・青は、色は選ぶが、**扱いは同じ**（高額品かどうかは紫・赤だけ）。古い記録の「黄・緑・青」（色を分ける前）は、そのまま読める。同じシールを別の商品に使うとエラー。
6. **送信・終了**: 訪問終了前チェックリスト（本人確認書類の登録・契約書の印刷と紙の署名・会社控えの回収・クーリング・オフ説明・代金のお支払い・梱包・数量一致・忘れ物の8項目）。GMOサインへ送信して訪問終了。
   - 契約書は、GMOサインで印刷する。**チェック項目・署名は、印刷した紙にお客様が記入する**（電子署名ではない）。
   - 訪問終了時に、シール付きの実物1点ごとに「入庫待ち」が登録される。
   - **査定したが売らなかったもの（見送り品）**を記録できる（売らなかった理由は聴取しない＝記録しない）。

### 1.7 お客様の評価（営業の記録）

- 営業が訪問ごとに記録する。**訪問中は入力しない**（現地買取の流れには評価の入力はない）。**訪問が完了した予定を予定表（昨日・今日）で選び、モーダルで登録**する。**お客様には見せない**。
- **未登録は目立たせる**: 訪問完了で評価が未登録の予定は、予定表のブロックを赤で強調して「★ 評価未登録」を出し、予定表の上の帯に未登録の件数と名前（タップで評価のモーダルを開く）を出す。詳細にも赤い「お客様の評価を登録する」ボタンを出す。登録済みなら★を表示し、修正できる。**日報にも、その日の訪問ごとに評価の状況を出す**: 未登録は赤い帯と「★ 評価を登録」ボタン（タップで同じモーダルを開く）、登録済みは「評価済み ★n」（タップで修正）。不在などの結果で終わった訪問は、評価の対象外。
- 記録する項目:総合★1〜5、態度（良好/普通/難あり）、リピート見込み、資力（高そう/普通/低そう）、次回時期、次回の商材、特記事項、メモ。
- **評価は訪問単位と、お客様単位の2種類を分けて管理**する。営業のタブレットは訪問ごと。お客様単位は配車係が登録する。
  - 初回訪問の評価は、お客様の評価が未登録なら、**お客様の評価の初期値に自動設定**される（2回目以降は自動設定しない）。

### 1.8 商品の持ち帰り（入庫）

→ 詳細は 5.2。営業が自分の商品を、営業所と一体の倉庫へ入庫する（納入先は選ばない）。**高額品（紫・赤）も、ほかの商品と同じようにタブレットから所属の倉庫に入庫する**（一覧に「高額品（あとで本社へ移動）」と出る）。本社へは、倉庫の担当が倉庫間移動で移す。

## 2. コールセンター（`/callcenter/index.html`）

運用の前提は次のとおり（依頼者からの指示。自動メモリにも記録済み）。**ここを外すと、後で連絡し直しが発生する。**

> **オペレーターは「仮確定」まで。** 担当営業も仮決定で、**お客様には営業の名前を伝えない**（日時だけ伝える）。
> **配車係が最終確定**する。主に**翌々日分を毎日**。確定した訪問だけが営業タブレットの予定に出る。
> 受付関連の画面・文言では「確定」ではなく**「仮確定」**を使う。営業名をお客様向けに出さない。

### 2.1 受付（オペレーター）

- **ヒアリング項目**（`callcenter/intake.js`）: 電話番号1・2、姓名（別入力）、フリガナ（必須）、性別（必須）、年齢（必須）、郵便番号、住所、希望日時、来電のきっかけ（チラシ）、売りたいもの、当日の立会い、ご同席者、大型品、駐車スペース、表札、前日確認の連絡時間帯、訪問時の注意。
  - **郵便番号から住所の候補**: 郵便番号を7桁入れる（ハイフン・全角は可）と、欄の下に住所の候補（都道府県〜町域）が出る。押すと住所に入り、カーソルが末尾に来るので、番地は続けて入力する。**候補は提案で、住所は自由に直せる**。表にない郵便番号は「見つかりません」と出し、住所は直接入力する。住所がすでに候補で始まっていれば、候補は出さない。候補の表は、モックでは主な町域だけ（`src/zipAddress.js`）。
  - **必須（確定に必要）**: 電話番号・お名前・フリガナ・性別・年齢・住所・来電のきっかけ・売りたいもの。他は聞き忘れの注意だけ。
  - **聞き取り状況**（聞いた✔／未）を項目ごと・上部パネルに表示して聞き忘れを防ぐ。「なし」と聞いた場合も聞いた扱い。必須は赤い＊。
  - **年齢を聞けなければ、声色から性別・年代を推測**して選べる。ただし**「推測」として区別して記録**する。
  - 立会いとご同席者は別項目。売りたいものは、メイン商材（背広・婦人服・婦人靴・紳士靴、数量帯）＋その他の商材＋詳細（複数行）。
- **来電のきっかけ**: チラシは**固有のID**（N/P/D＋4桁）で特定する（広告の種類だけでは、どの号か決められないため）。IDのない広告（ネット・テレビ・紹介・再利用）のみ言葉から判定。
- **過去のお客様**: 電話番号（1・2）が一致すれば、情報を引用できる。直近の買取額・依頼回数・総買取額、**電話番号ごとの受電履歴**を表示。オペレーター向けの表示は最小限。
- **エリア判定**（`src/dispatch.js`）: 訪問先の**都道府県**から担当エリアを決め、そのエリアの営業だけを候補にする（電話は全国から来るため、お客様の住所で判定）。

  | エリア | 都道府県 |
  |---|---|
  | 大阪 | 大阪・奈良・和歌山 |
  | 兵庫・京都 | 兵庫・京都・滋賀 |
  | 関東 | 東京・神奈川・埼玉・千葉・茨城・栃木・群馬 |
  | 東海 | 愛知・岐阜・三重・静岡 |

  担当のない都道府県は「対応エリア外」とし、他エリアの営業を例外として選べる。**ただし、希望日に出張（7.4）がある都道府県は、出張エリアとして判定する**。**判定は提案**で、オペレーターがGoogleマップで位置を確認してエリアを確定する。
- **空き確認**: 営業時間 9:00〜19:00、30分刻み、訪問は60/90/120分。**訪問の前後30分は移動時間として確保**。営業の予定と確定済み予約から空きを判定。欠勤は選べず表示。**午後出社・午後半休**も反映（休みの時間には訪問が入らない）。空き開始時刻は人数つきで一覧。
- **カレンダー**: 1週間ごとの週表示（1行の一覧）と、日別表示（営業ごとの列）。営業の顔写真・ランク・得意分野・前の訪問からの距離（前の訪問がなければ距離は出さない）を表示。**どの枠を選ぶかはオペレーターが決める**（システムが候補をあらかじめ選ぶのはOK）。
- **公平な配分**: **女性のお客様は客単価が高いため、今月の「女性のお客様の担当件数」が少ない営業をおすすめ**する（男性のお客様は担当件数の少ない順）。おすすめ以外を選ぶと、より担当の少ない営業がいることを知らせる。
- **営業にはランク（S〜C、仮の設定）と得意分野**がある。大阪エリアは営業10名。実績・担当件数はダミー。
- **仮確定**: 通話を終えても**自動確定しない**。枠と担当の最終決定はオペレーターが行う。

### 2.2 仮確定後の変更・取消（折り返しの電話）

お客様から「やっぱりやめる」「日を変えたい」と電話が来ることがある。

- 電話番号で既存の受付を見つけ、**全項目を変更**・取消ができる。取消は**理由つきで記録を残す**（理由: お客様のご都合・入力ミス/重複・会社の都合・その他）。履歴が残る。
- **確定済みをオペレーターが変更すると、仮確定に戻り、配車係に知らされる**。

### 2.3 配車確定（配車係）

- 営業ごとの列のカレンダーのみ（一覧表示は廃止）。**予約をドラッグして営業・時間を調整**できる。営業の元からの予定も予約として取り込んで動かせる。
- 色: 仮確定=薄い青／確定済み=濃い青。「未確定の仮確定」と「確定から仮確定に戻った訪問」は色分けし、変更内容をカレンダー下の詳細に表示。休みと重なる予定は警告。
- 訪問間の移動距離と、営業ごとの1日の総移動距離を表示。営業のランクと今月の担当件数の偏りを見て判断する。
- **お客様の詳細モーダル**（配車係が誰を当てるかを判断する材料）: 買取履歴（品目ごと全件・折りたたみ）、営業の評価・メモ（訪問ごと）、前回までの担当、ランク・厄介度・クーリングオフ歴、見送り品。
  - **顧客ランク**（S〜C）: 登録がなければ、**総買取額から自動**（100万円以上=S、50万=A、20万=B、実績あり=C、なし=新規）。
  - **厄介度**（なし/注意/要注意）: **人が登録したものだけ**。営業の評価から自動で上げない（自動判定は廃止した）。
  - **クーリングオフ歴**は契約の記録。お客様の評価を登録し直しても消えない。
- **配車係の権限ルール（重要）**: 確定権があるので、**配車係が何を入力・変更しても、状態は変えない**（確定済みは確定のまま）。お客様に連絡して回答次第で決めたいときだけ、配車係が意図的に**「仮に戻す」（確認待ち）**。
- 「空き状況・受付履歴」画面は削除済み。

### 2.4 音声入力デモ（今後の拡張）

通話デモは別ウィンドウ（`?demo=1`）。台本を1発話ずつ／最後まで一気に進められ、お客様の発話から項目を拾って入力欄に自動セットする。**あくまでデモ。基本はオペレーターの手入力で完結させる**前提で、デモは通話終了でも訪問を自動確定しない。

### 2.5 クーリングオフの受電と依頼（`?tab=cooloff`）

クーリングオフは、**お客様から電話がかかってきて始まる**（専用の番号。受けるのはコールセンターのオペレーター）。**依頼を作るのはコールセンター、返送・完了の対応をするのは倉庫**。（以前は倉庫担当が返品を「受付」していたが、依頼に一本化した。倉庫の画面に受付の入力欄はない。）

> お客様の電話 → オペレーターが商品を検索し、状態を確認 → **依頼を作成**（システム上で倉庫へ問い合わせ）→ 倉庫が回答 → 返送 → お客様の手元に商品が戻り、**買取代金の返金**も済んで**完了**。進捗は依頼ごとに管理する。

- **商品の検索（オペレーターが探しやすいUI）**: お客様は、手元に商品がないまま「先週の金曜日に来てもらった山田ですが、そのとき売った時計を返してほしい」のように、**うろ覚えの手がかり**で電話してくる。**実際には買い取っていない可能性**や、**似た商品が複数あってそのうちの1つだけ**の可能性もある。そのため、次の点を守る。
  - **商品の写真を、検索結果に大きく出す**（押すと拡大）。**写真を見せながら「これですか」と確認**できないと、電話の会話が成り立たない。写真は、**倉庫で登録した写真**（5.3）、なければ買取のときの査定依頼の写真、それもなければ商品名から作ったダミー（モック）を使う。本実装では、買取時の撮影写真を商品に必ず紐づける前提。倉庫の依頼の画面にも写真を出す（棚から探しやすい）。
  - **手がかりはどれでも探せる**: **電話番号**（買取データは、訪問→お客様を通じて、受付でヒアリングした電話番号1・2に紐づく。モックでは、買取のとき商品に番号を控える。ハイフンの有無・4桁以上の一部でも可）・お名前（空白の有無を問わない。同じ名字が複数いても、買取日で絞れる）・シールNo.・商品名・商品の種類（「時計」でカテゴリにも当たる）・**買取日**（直近14日を「10/24(金)」のように曜日つきで並べ、その日の契約の数を添える。複数選べる）・商品の種類のボタン。名前を外して買取日だけ、でも探せる。種類を選ぶと、その商品だけを出す。
  - 結果は契約（お客様・買取日）ごとにまとめ、商品ごとに状態の目印を出す: 在庫・期間内／**期間超過**（倉庫が個別に判断）／出品中・委託中・入庫前など（倉庫に確認）／**売却済み（対応不可）**／すでに依頼中／返品済み／輸送中・梱包中（届く・発送が済むまで依頼できない）。
  - 見つからないときは、「買い取っていない可能性もある」ことと、探し直す方法（名前を外す・買取日を広げる）を知らせる。
- **依頼の作成**: 商品・電話番号・理由・受電メモ・受けたオペレーターを記録。依頼は**倉庫ごとに分かれる**（5.7）。売却済みの商品は、対応不可の依頼として記録だけ残す。
- **倉庫の回答**（5.7）で、返送できれば返送の準備へ、**対応できなければ理由つきで「対応不可」**として終わる。オペレーターは進捗を見るだけで、回答・返送・完了の操作はできない。
- **進捗の段階**: 受電・依頼 → 倉庫の回答 → 返送 → 代金の返還（`returnSteps`）。依頼ごとに、倉庫との**やり取り（チャット）**を開いて見られ、メッセージも送れる（5.7）。倉庫の回答待ちの件数が、タブに出る。

### 2.6 来店予約（`?tab=store`）

店舗への**来店予約**を、オペレーターが電話で受ける（`callcenter/storeTab.js`）。訪問買取の受付（2.1〜2.3）とは**別の流れ**で、**エリア判定・担当営業の割り当て・仮確定・配車確定はない**（お客様が店舗へ来る側のため）。

- **項目**: 店舗（有効な店舗から選ぶ）・来店の日（今日以降）・時刻（10:00〜18:30、30分刻み）・電話番号（必須）・お名前（必須）・フリガナ・売りたいもの。受けたオペレーターが記録に残る。
- **過去のお客様**: 電話番号を入れると、過去の買取（回数・総額・顧客ランク・厄介度・クーリングオフ歴）があれば、その場で出る（訪問買取の受付と同じお客様の履歴を使う）。
- **一覧**: これからの来店予約を、日ごと・時刻順に出す（全店舗）。**取消は理由つき**（受付の取消と同じ4つの理由）で記録が残る。取消は、店舗が来店済みにする前まで。
- 予約は、店舗の画面（11章）の「これから来店の予約」に出る。**状態は「予約」だけ**で、「仮確定・確定」は使わない。

## 3. 査定部（`/honsha/index.html`）

- **担当**: 査定員（青木=グループA、井上=グループB。マスタ管理の社員で登録、7章）が、担当グループの営業の**今日の予定（時系列）と訪問状況**を見る（デモ用に査定員を切り替え可。完了した訪問は隠せる）。
- **買取明細のリアルタイム表示**: 営業が登録した商品・金額・ランク・数量・売る/売らない・本社査定の状況・コメント。**営業のお客様の評価**も確認できる。
- **査定依頼のチャット**: 商品を選ぶと、営業とのチャットが開く（営業は左、査定員は右。写真・「既読」つき）。**普通のチャットと同じ**で、メッセージを入力して「返信する」（Ctrl+Enter でも送れる）。査定部はPCなので、**タグ・定型文のボタンはない**。任意で提案査定額（ランクは営業の入力のまま）を付けられる。チャットと違うのは、査定依頼ごとに**「完結する」**操作がある点だけ。**送信フォームは1つ**（回答と意見の区別なし）。営業の返信が未読の商品は、一覧に「未読あり」が出る。**査定員が「完結する」**とやり取りが終わる。完結のあとに営業が続けて送ると、再開（返信待ち）になる。査定依頼のない商品へのコメントは、これまでどおり営業のコメントとして届く。
- **承認／差戻し**: 営業の申請は不要で、**商品が登録された時点からいつでも**実行できる。金額が入っていない商品は対象外。**査定依頼が出ている商品は、完結するまで承認できない**（ボタンは押せず、一覧には「査定の完結待ち」）。**承認の欄は、チャットの上に固定で表示**し、査定依頼が続いている間は、隠さずに**マスク**（薄く表示して操作不可）する。**差戻しも、完結してから**。依頼のない商品は、いつでも承認できる。「承認できるN件を一括承認」は、条件を満たす商品だけ。**差戻しは理由必須**で、営業には❗コメントとしても届く。承認後に営業が変更したら再承認が必要。
- **お知らせ送信**: 全員／グループ宛のメッセージを作成して、営業のダッシュボードに表示。
- 入金・日報の機能は**経理部へ移した**（査定部にはない）。

## 4. 経理部（`/accounting/index.html`）

画面: 所持金の確認／入金処理／経費の入力代行／経費の全体状況。**左側の開閉式メニュー**（☰で開き、項目を選ぶか、外側・✕で閉じる。営業のタブレット・倉庫・物流と同じ）で切り替える。**営業所（担当エリア）で全画面を絞り込める**（上部の選択）（全営業所のときは、各営業の所属営業所を併記）。ロジックは `src/accounting.js`。

- **所持金の確認**: 営業ごとの所持金・明細。**確認事項**を自動検知する（日ごと）:
  - 始業時の繰越金の差異（警告）／終業時の過不足（危険）／帳簿残高がマイナス（危険）／所持金が **50万円超**（警告）。
  - 経費: **1万円以上**の高額（警告）／用途が「その他」（情報）／レシート写真なし（警告。経理代行は除く）。
  - 閾値は `HIGH_EXPENSE`・`CASH_LIMIT`。
- **入金処理**:
  - 営業への入金: 営業・金額・メモ。毎朝の定例入金（ダミー）は一覧に出さず、経理部が登録した分だけ出す。
  - **お客様への入金（銀行振込）**: お客様名・金額・理由（営業の現金が足りなかった／高額のため後日振込／その他=メモ必須）・担当営業（任意）・メモ（振込先口座など）。未入金→入金済みを記録。担当営業が未指定の振込は、全営業所のときだけ表示。
- **経費の入力代行**: 営業のレシート紛失などの代行入力。**内容・理由は必須**。**業務中（始業済み・未終業）の日だけ可能**（終業後に足すと、営業が数えた現金と帳簿が合わなくなるため）。「経理代行」の印が付く。
- **経費の全体状況**: 今日／今月。種別別・営業別の集計。買取代金は経費に含めない。
- サンプルデータは、記録が空のときだけ自動投入。営業側の更新は即時反映（入力中は入力欄から離れたときに反映）。

## 5. 倉庫・物流（`/warehouse/index.html`）

営業が入庫した買取商品（シールNo.ごとの実物1点）を、フリマ・業者に販売して利益を得るための画面。**画面ごとの操作は README の「倉庫・物流」の節が詳しい**ので、ここでは決定事項（ルール）を整理する。ロジックは `src/warehouse*.js`・`src/shipping.js`・`src/stock.js`。

### 5.1 ログインと倉庫マスタ（倉庫・物流の画面にはない。マスタ管理で編集）

- 倉庫担当ごとにログイン（`wh01`〜`wh05`、パスワードは何でも可。**倉庫担当は、マスタ管理の社員（7章）で登録する**）。**所属する倉庫が、入庫先と表示の対象**になる（上部の「対象の倉庫」で全倉庫・他倉庫に切替可）。操作はログインした倉庫担当の名前で記録される。
- **倉庫は営業所とは独立した施設**として管理（全国に複数）。営業所と一体／倉庫のみ／倉庫のない営業所（営業のみ）がある。初期値: 大阪倉庫（大阪営業所と一体）・関東倉庫（関東営業所と一体）・福岡倉庫（倉庫のみ）・本社。**兵庫・京都、東海の営業所には倉庫がない**。
- 倉庫ごとに名前・郵便番号・住所・電話番号（**伝票・CSV出力に必要**）・営業所との関係・保管場所（棚）・有効/無効を登録。**保管中の商品や有効な倉庫担当がいる倉庫は無効にできない**。倉庫担当は各倉庫に所属する（登録・所属変更・有効/無効は、マスタ管理の社員）。**倉庫・委託先・高額品の判定の編集は、倉庫・物流の画面ではなく、マスタ管理（7章）で行う**（倉庫・物流のメニューに、マスタ管理への入口がある。伝票・CSVの情報が足りないときも、マスタ管理で登録する）。
- **委託先（業者）**も同じ画面で登録（名前・郵便番号・住所・電話番号。初期値は大阪時計オークション・東京ブランド市場・関西貴金属市場）。
- マスタは「データ初期化」では消えない。メニューは左上「☰」の開閉式。入庫待ち・受け取り待ち・返品対応中の件数がメニューに出る。

### 5.2 入庫と、シールの色・高額品

- **本社も保管場所の1つ**（倉庫マスタに1か所だけ）。**シールの色が紫・赤の高額品も、まず営業所と一体の倉庫に入庫**する（営業は色にかかわらず同じ操作。QRの色で納入先は変わらない）。**そのあと、倉庫間移動で倉庫から本社へ移す**。本社には、入庫ではなく移動でだけ入る。
  - 色は紫（最も高額）・赤・黄・緑・青の5色だが、**高額品の判定は紫・赤だけで、黄・緑・青の扱いは同じ**（色は営業・店舗スタッフが選ぶ。古い記録の「黄・緑・青」は、そのまま読める）。本社へ移す色は倉庫マスタ画面で変更できる。
  - 色は基本的に営業が決める（査定部と相談することもある）。
  - 1契約に高額品とそれ以外が混ざっても、全て同じ倉庫に入庫し、高額品だけを後で本社へ移す。
- **入庫の規則**: 色にかかわらず、**倉庫の担当が入庫する。本社には入庫できない**（本社の倉庫担当の入庫タブは、入庫できない旨が出る）。**倉庫間の移動の規則は、これまでどおり**（高額品は本社だけへ、高額品以外は本社以外の倉庫だけへ移せる）。
- **倉庫担当の入庫**: 契約ごとに、明細と実物を見比べて、一致した商品に☑を付けてから入庫。☑は誰がいつ付けたかが残る。スキャナ・手入力（シールNo.）の場合は「読み取りで照合した」記録。誰が買い取った商品でも入庫できる。**保管場所は、訪問買取は「クーリングオフ保管棚」に固定**（棚は選ばない）。**店頭買取（クーリング・オフの対象外）だけ、入庫先の棚を選ぶ**。
- **営業の入庫**（タブレット）: 最初の操作は、**商品に貼ったシールのQRの読み取り**（画面の最上段の大きなボタン。QRが読めないときだけ、下のシールNo.入力）。自分の商品を、**納入先の倉庫は選ばず**、自分の営業所と一体の倉庫（なければ先頭の倉庫）に入庫する。**画面は、左に一覧・右に入庫の操作ではなく、左が「入庫する」、右が一覧**。**入庫した商品は一覧から消さず、グレーの「入庫済み」にして、各訪問の下へ回す**（上が未入庫、下が入庫済み。未入庫が残る訪問が先）。**保管場所（棚）は選ばない**。クーリングオフ期間中は商品ごとに分別せず、**全て「クーリングオフ保管棚」にまとめて保管**する。この場合、倉庫での照合の記録は残らない。入庫済み・他の営業の商品・未登録のシールはエラー。手元にない商品は「所在不明」として報告できる。対象日で絞り込み（1日分でも、2〜3日分まとめてでも可）。
- **シールの貼り替え**: 色が間違っていた場合（新しいシールのQRから色が自動で選ばれる）、**シール自体が別になるので、商品のシールNo.（ID）も新しくなる**。古いNo.・色は履歴に残り、移動などの記録は新しいNo.に引き継がれる。古いシールを読み取ると、貼り替え済みと新しいNo.が出る。**貼り替えられるのは、入庫前・所在不明・在庫の商品のみ**（出品中・委託中・売却済み・返品対応中・輸送中は不可）。納入先が変わる場合は、倉庫間移動で本社・倉庫に移すよう案内する。営業は訪問を終える前なら、タブレットでシールを「解除」して読み取り直す。

### 5.3 商品管理

- 状態: 入庫待ち／在庫／出品中／売却済み／返品。検索は**1つの欄**（商品名・シールNo.・お客様名。QRリーダー・手入力のEnter・カメラ（モック）で読み取れる）。読み取ると、詳細と、買取から入庫・出品・売却・返品までの履歴を表示。
- 表示は「一覧」（初期表示）と「買取日・お客様別」（契約単位にまとめる。クーリングオフ時にすぐ探せる）。QRで探すと、**同じ契約で買い取った他の商品とその保管場所**も出る。
- **商品の写真の登録（倉庫）**: クーリングオフの電話で、お客様と商品を確認するための写真。商品管理の一覧・詳細、入庫の一覧の写真を押すと、撮影・選択して登録（撮り直し）できる。**誰がいつ登録したか**が残る。削除するとダミーの絵に戻る。**未登録は印（未登録）で見分けられ、「写真未登録」で絞り込める**。在庫の操作ではないので、**どの倉庫の商品でも登録できる**（5.5 の制限の対象外）。
- ページ送り: 20/50/100点（買取日・お客様別は契約の件数で分割）。絞り込み・検索・表示切替で1ページ目に戻る。

### 5.4 パックの流れ（共通）

倉庫間移動・委託・購入者への発送は、**同じ「パック」の流れ**で統一している（`src/shipping.js`、画面は `warehouse/packUi.js`）。

> ① 商品を探して入れる（検索・QR読取）→ ② パッキング（配送業者・サイズ60〜170・個口数・メモ）→ ③ 明細（書類）を出力 → ④ 発送伝票とCSVを出力 → 発送（追跡番号）

- 配送業者はヤマト運輸・佐川急便・日本郵便・その他。CSVは各社の取込用（UTF-8、個口ごとに1行、複数パックのまとめて出力可。**列の並びは仮で、実際の取込形式に合わせて調整が必要**）。
- 梱包中の商品は「梱包中」になり、出品・返品・別のパックには使えない。入れられない商品は理由が出る（登録なし・貼り替え済みの古いシール・在庫でない・他の倉庫・別のパック・送り先の規則違反）。
- 明細・伝票の出力は日時が記録され、**未出力のまま発送するときは確認が出る**。送り先の郵便番号・住所・電話番号が足りないと、伝票・CSV出力のときに知らせる。

| パックの種類 | 書類 | 載せるもの／載せないもの | 発送後 |
|---|---|---|---|
| 倉庫間移動 | 送付明細 | 商品・買取額・合計・受領確認欄 | 「輸送中」。受け取るまで**どちらの在庫にも数えない**。送った倉庫は輸送中なら取り消せる |
| 業者への委託（業者オークション） | 委託明細 | **希望価格のみ。原価・お客様の情報は載せない** | 「委託中」（倉庫の外）。売れたら入金額を登録（委託手数料を引いて売上に反映）、売れ残りは倉庫の在庫に戻る |
| 購入者への発送（フリマ・業者直接販売） | 納品書 | **商品名と売価のみ。原価・買い取ったお客様・シールの色は載せない**。敬称は「様」 | 売却済みのまま。発送日時・追跡番号が履歴に残る。購入者情報は梱包中に直せる |

- 移動先の倉庫担当は、届いた商品に☑を付け、自分の倉庫の棚を決めて受け取る。送れるのは在庫だけ（出品中・委託中・返品対応中は先に戻す）。
- 委託の希望価格は、原価の1.3倍の目安が入る。高額品も委託できる（移動先の規則は倉庫間の移動のみ）。
- 委託先の市場で売れた商品は、市場が購入者へ送るため、購入者への発送の対象外。
- サンプルデータでは、どの倉庫・本社の倉庫担当でログインしても、梱包中・受け取り待ち・輸送中・履歴のダミーが見える。

### 5.5 自分の倉庫の商品だけ扱える

出品・売却・価格変更・返品の対応は、**ログインした倉庫担当の所属倉庫の商品だけ**。他の倉庫の商品は、先に倉庫間移動で自分の倉庫に移す（商品管理では他倉庫の商品も見られる）。

### 5.6 販売（出品）・売上管理

- 販売先と手数料率（**ダミー**）: メルカリ10%・ヤフオク10%・ラクマ6.6%・業者オークション3%（委託）・業者へ直接販売0%。売れたら、実際の売価・送料・購入先を登録（手数料は料率で自動計算）。出品中の価格変更・取り下げも可。
- **出品価格の目安は原価の1.3倍**（千円単位に切り上げ）。
- **売上管理**: 今日・今月・全期間の売上・原価・手数料・送料・利益・利益率を、販売先別・カテゴリ別に集計。集計対象は自分の倉庫（初期値）／他の倉庫／**会社全体**（倉庫別の内訳も出る）。

### 5.7 クーリングオフ返品

- **対象は訪問買取の商品だけ**。**店頭買取（11章）の商品は、法律上クーリング・オフの対象外**なので、この保管期間（10日間）もない（入庫したその日から出品できる）。コールセンターのクーリングオフの検索には「店頭買取（クーリング・オフの対象外）」と出て、依頼にはできない。
- 法律上は書面を受け取った日（買取日）から**8日間**。お客様の通知は郵送で届くため、余裕を見て**買取から10日間（`COOLING_OFF_DAYS`）は販売せず保管**する。
- 保管期間中の商品は**出品できない**（「○/○まで出品不可」と表示）。期間を過ぎた入庫済みの商品から出品できる。
- **依頼はコールセンターが作る**（2.5）。倉庫の画面は、その依頼への対応だけを行う（受付の入力欄はない）。依頼は問い合わせを受ける倉庫（入庫前の商品は納入先になる倉庫。高額品も、いったん倉庫に入る）ごとに分かれ、`groupId` で同じ契約として結びつく。
- **画面は「一覧」と「詳細（モーダル）」**。一覧はお客様名・電話番号・商品名・シールNo.・依頼番号・理由・メモで**検索**でき、すべて／未対応／対応中／完了・対応不可に絞れる（件数つき）。**未対応の依頼は、一覧の上部の帯・行の色・「未対応: ○○」の印、メニューの件数**で分かる。未対応は、**回答待ち**・**返送待ち**・**コールセンターからの未返信のメッセージ**（倉庫の最後の対応より新しいもの）。返送済みで返金待ちの依頼は、倉庫がすることがないので未対応に数えない。
- **詳細には、その依頼のやり取りが、チャット形式で時系列に並ぶ**（コールセンターは左・倉庫は右・システムの記録は中央）。受電・倉庫の回答・返送・完了の出来事が自動で並び、コールセンターと倉庫が**自由にメッセージを送り合える**（Enterで送信。完了・対応不可のあとも送れる）。回答・返送・完了の操作も、詳細から行う。**入力欄は1つ**で、回答のときは、その内容が回答のメモとして、やり取りに残る（「対応できない」は理由が必須）。コールセンター側の進捗でも、同じやり取りを開いて、メッセージを送れる（操作は送信のみ）。
- 流れ: **倉庫に問い合わせ中** → 倉庫が回答 → **返送の準備中** → **返送済み**（追跡番号）→ **お客様からの買取代金の返還を確認して完了**。完了した商品は「返品済み」で在庫から外れる。理由: 家族に反対された／金額に納得できない／手放したくなくなった／その他。
- **倉庫が対応できないと回答**したときは、**理由が必須**で「対応不可」になり、商品は元の状態に戻る（そのあとで改めて依頼もできる）。**売却済みの商品**の依頼は、回答を待たず「対応不可」として記録する。
- **期間を過ぎた商品も依頼は作れる**（「期間超過」の印が付く）。受け付けるかは倉庫が個別に判断する。出品中・委託中・入庫前などの商品も、依頼を作って倉庫が回答する。**輸送中・梱包中の商品は、届く・発送が済むまで依頼できない**（移動・委託・発送のパックを壊さないため）。
- 問い合わせ中は、在庫の商品だけ出品できなくなる（ほかの状態の商品は、倉庫が「返送できる」と回答するまで状態を変えない）。
- 契約の商品が複数の保管場所（本社と倉庫）に分かれていても、**契約全体で依頼を作り**、保管場所ごとの返品に分かれる（お客様に返していただく代金は契約全体の合計）。それぞれの倉庫担当が回答・返送・完了の対応をする。他の倉庫の依頼は扱えない。

## 7. マスタ管理（`/master/index.html`）

各画面で使う**基本のデータ（マスタ）**を、1つの画面で管理する。**社員・部署・営業所・出張・店舗・倉庫・委託先**の7つ（会社は、REqualの1社だけで、マスタとしては持たない）。画面は `master/`、ロジックは `src/employees.js`・`src/departments.js`・`src/offices.js`・`src/trips.js`・`src/stores.js`・`src/warehouseMaster.js`。用語は用語集のとおり。

- **メニュー**: 倉庫・物流、営業タブレットと同じ、**左側の開閉式メニュー**（☰で開き、項目を選ぶか、外側・✕で閉じる）。マスタ（社員・部署・営業所・出張・店舗・倉庫・委託先）はここで切り替える。
- **共通のルール**: 削除はなく、**有効・無効だけ**（過去の記録に名前が残っているため）。保存は localStorage で、**「データ初期化」では消えない**。画面の「初期値に戻す」で、すべて見本に戻る。
- **モックのため、データどうしの連動は最小限**。ダミーのデータは、ダミーのまま割り切る（連動する範囲は、下の各マスタに書いたとおり。連動しない部分は、本実装のときに決める）。

### 7.1 社員

社内の社員（営業・オペレーター・配車係・査定員・経理担当・倉庫担当・店舗スタッフ）の**名簿**。**社員は、いずれかの部署（7.2）に属する**（部署は、社員ごとに選ぶ。役割とは独立した項目で、役割ごとの初期の部署が入る: 営業→営業部、オペレーター・配車係→コールセンター、査定員→査定部、経理担当→経理部、倉庫担当→物流部、店舗スタッフ→店舗部）。一覧には部署の列と、部署での絞り込みがある。

- **1人にひとつの役割**。**役割は、登録したあとは変えられない**（役割ごとに持つ項目も使える画面も違い、記録の社員名と食い違わせないため）。別の役割にするときは、新しく登録して、いまの社員を無効にする。
- **役割ごとの項目**（氏名・ログインID・部署は共通）:

  | 役割 | 追加の項目 | 反映される画面 |
  |---|---|---|
  | 営業 | グループ・グループリーダー・営業所（表示のみ） | **参照のみ**（下記） |
  | オペレーター | なし | コールセンター上部の「オペレーター」の選択肢。受付・クーリングオフの依頼・やり取りの記録に、この名前が残る |
  | 配車係 | なし | いまは名簿だけ（画面で人を区別していない） |
  | 査定員 | 担当グループ（A・B、複数可） | 査定部上部の「査定員」の切り替え。担当グループの営業の予定・訪問を見る |
  | 経理担当 | なし | いまは名簿だけ（画面で人を区別していない） |
  | 倉庫担当 | 所属倉庫（有効な倉庫から選ぶ） | 倉庫・物流のログイン（有効な人だけ）。倉庫マスタには所属の一覧を出す（参照のみ） |
| 店舗スタッフ | 所属店舗（有効な店舗から選ぶ） | 店舗のログイン（有効な人だけ）。店舗マスタには、店舗ごとの人数を出す。ログインIDは `st01`〜 |

- **営業は、ここでは参照のみ**（登録・変更・無効化はできない）。営業の業績・担当エリア・始業終業・経費などの記録が、各画面に固定されていて、まだ名簿とつながっていないため。つなぐときは、`USERS`（`src/dashboard.js`）・`areaOfUser`・営業タブレットのログイン（`src/auth.js`）を、名簿から読む形に変える。
- **削除はなく、有効・無効だけ**（過去の記録に、社員の名前が残っているため）。無効にすると、ログインや選択肢に出なくなる。**役割ごとに、有効な社員を最低1人は残す**（最後の1人は無効にできない。オペレーターや査定員の選択肢が空になるため）。**店舗が無効にできるのは、有効な店舗スタッフがいなくなってから**（7.7）。
- **ログインID**: 英数字・ハイフン・アンダースコアの3〜20字。小文字にそろえ、**役割をまたいで重複不可**。パスワードの管理はない（モックは何でも通る）。
- **一覧**: 役割ごとの人数つきの見出し、氏名・ログインIDの検索、有効/無効の絞り込み。
- **保存**: localStorage（`rq-mock-users`）。**「データ初期化」では消えない**（マスタ扱い）。画面の「初期値に戻す」で見本に戻る。以前の保存形式（倉庫マスタの中の倉庫担当）は、最初に開いたときに引き継ぐ。
- **見本の社員**（ダミー）: 営業16名（既存のとおり）・オペレーター2名（佐藤・渡辺）・配車係1名・査定員2名（青木・井上）・経理担当1名・倉庫担当5名（`wh01`〜`wh05`）・店舗スタッフ3名（`st01`・`st02` なんば店、`st03` 新宿店）。配車係・経理担当は、画面で人を区別していないため、見本の1名だけ。


### 7.2 部署

- 会社「REqual」（1社だけ。画面でも変更できない）の部署の一覧・登録・変更・有効/無効（`src/departments.js`、保存は `rq-mock-departments`）。見本は、営業部・コールセンター・査定部・経理部・物流部・店舗部（店舗スタッフの所属）。店舗部がない古い保存は、読み込むときに店舗部を足す。**階層（課・チーム）はなく、並べるだけ**。名前は重複不可。
- **有効な社員がいる部署は、無効にできない**（先に社員を別の部署へ移す）。有効な部署は最低1つ残す。一覧に、部署ごとの有効な社員の人数が出る。
- 部署と、営業所・倉庫は別のもの（部署＝組織の単位、営業所・倉庫＝拠点・施設）。つながっていない。

### 7.3 営業所

- 営業所（名前・担当の都道府県）の一覧・登録・変更・有効/無効（`src/offices.js`、保存は `rq-mock-offices`）。名前は「営業所」を付けない短い名前（大阪）で、画面では「大阪営業所」と出す。名前は重複不可。担当の都道府県は、47都道府県の名前から選んで入力する（カンマ・読点・空白・改行で区切る。なくてもよい）。**有効な営業所は最低1つ残す**。

- **つながっているのは、倉庫の「営業所との関係」の選択肢だけ**。訪問先のエリア判定・配車（`AREAS`、2章）・営業の所属は、まだ営業所マスタを見ていない（出張エリアは別で、7.4のとおりエリア判定・配車につながっている）。見本の4営業所は、既存の担当エリアと同じ。

### 7.4 出張

営業所のない都道府県へ、**チラシを配って、1週間ほど限定で訪問買取をする**営業方法。営業所の担当エリアは全国をカバーしていないため、**出張エリア（期間つきの臨時のエリア）を作って、そこへ行く営業（出張メンバー）を入れる**（`src/trips.js`、保存は `rq-mock-trips`）。

- **項目**: 名前（例: 福岡出張。重複不可）・担当の都道府県（1つ以上）・期間（開始日〜終了日。両端を含み、1日だけでもよい）・出張メンバー（営業を1人以上）・有効/無効。削除はなく、有効・無効だけ。一覧に、出張中／これから／終了の状態が出る。
- **担当の都道府県は、営業所のあるエリア（2.1の表）の都道府県を選べない**（出張は、営業所のないエリアへ行くもの。営業所の担当エリアと重ならないので、判定が一意に決まる）。
- **出張メンバーの本来の営業所は変えない**。**期間中は、出張エリアの候補になり、本来の営業所のエリアの候補にも残る**（配車係・オペレーターが空きを見て決める。どちらかを外すことはしない）。**出張中であることが分かるよう、「🧳 出張中（出張の名前）」の印**を、受付の担当候補・日別カレンダーの列の見出し・配車確定の営業の列・営業の詳細に出す。
- **エリア判定への反映**（2.1）: **希望日が出張の期間内**であれば、出張の都道府県のお客様の住所は「出張エリア」と判定され、出張メンバーが候補になる（エリア確定のボタンにも「🧳 福岡出張」が出る）。期間外・無効な出張は、従来どおり「対応エリア外」。
- **モックのため、連動は最小限**: エリア判定・担当候補・受付／配車の表示まで。営業タブレット（予定・業績）・経理部の営業所の絞り込み・倉庫の入庫先には、まだつながっていない。チラシ（来電のきっかけ）のIDとの結びつけもない。出張の期間が終わった後の受付には、出張の名前が残る。
- **見本**（ダミー）: 今日を基準に、福岡出張（出張中）・四国出張（これから）・北海道出張（終了）の3つ。

### 7.7 店舗

- **項目**: 名前・郵便番号・住所・電話番号・営業時間・**古物商許可番号（必須。古物営業法は、許可を営業所（店舗）ごとに求めるため）**・納入先の倉庫（倉庫マスタの、本社以外の有効な倉庫）。
- **有効な店舗スタッフ（7.1）がいる店舗は、無効にできない**（先に、社員を別の店舗へ移すか、無効にする）。一覧に、店舗ごとの店舗スタッフの人数が出る。
- **営業所とは別のマスタ**（つながっていない）。店舗と営業所が同じ建物でも、別々に登録する。
- **モックのため、連動は最小限**: 納入先の倉庫は、いまは店舗マスタの記録だけ（倉庫の入庫は、これまでどおり、倉庫担当が自分の倉庫へ入庫する）。営業時間は、来店予約の時刻の選択肢（10:00〜18:30）にまだつながっていない。契約書・古物台帳への許可番号の印字もない。
- **見本**（ダミー）: なんば店（納入先は大阪倉庫）・新宿店（納入先は関東倉庫）。「初期値に戻す」で見本に戻る。

- 手数料率・営業のランク・エリア境界・クーリングオフ保管日数（10日）など、運用で決まる値の確定。
- 青いシールの扱い（1点では出品できないが、現状は区別していない）。
- **店舗（11章）の未対応**: レジ現金（始業・終業の現金照合・前日繰越金・経理部への反映。営業の現金管理と同じ形にする予定）、査定部への査定依頼・承認（店頭買取は、いまはスタッフが金額を入力するだけ）、経理部の店舗での絞り込み、業績の店舗別の集計、店舗の営業時間と来店予約の時刻の連動、納入先の倉庫への連動、古物台帳（買取の記録の帳簿）と、契約書への古物商許可番号の印字。
- **店頭用の契約書の様式**: GMOサインの契約書（`gmosign/contractForm.js`）は、訪問買取の様式のままで、クーリング・オフの記載がある。店頭買取は対象外なので、様式を分ける必要がある（法務の確認が要る）。説明事項の「対象外であること」の文言（`src/storePurchase.js`）も、法務の確認が要る。

## 11. 店舗（店頭買取）（`/store/index.html`）

**お客様が店舗に買取希望品を持ち込む**買取。訪問買取（1〜6章）と**別の流れ**で、**訪問・エリア判定・担当営業の割り当て・配車・移動距離はない**。画面は `store/`、ロジックは `src/storeVisits.js`（来店）・`src/storeDraft.js`（買取の作業中の内容）・`src/storePurchase.js`（完了の記録）・`src/storeSession.js`（ログイン）・`src/storeSample.js`（見本）。用語は用語集（店舗・店舗スタッフ・店頭買取・来店・来店予約・飛び込み）のとおり。

> **店頭買取は、クーリング・オフの対象外**（法律上、対象は訪問購入のため。依頼者に確認して決定）。買い取った商品には、**10日間の保管期間（5.7）がなく、入庫したその日から出品できる**。
> 古物営業法に基づき、**本人確認**と、買取の記録に要る**氏名・住所・職業・生年月日**を、お客様確認で入力する。古物商の許可は店舗ごとに必要（7.7）。

### 11.1 ログインと画面の構成

- 店舗スタッフごとにログイン（`st01`〜。パスワードは何でも可。**店舗スタッフは、マスタ管理の社員（7.1）で登録する**）。**所属する店舗が、表示の対象**。受付・買取は、ログインした店舗スタッフの名前で記録される。
- 画面は、**来店（一覧）**と**買取（5手順）**の2つ。上部に、店舗名・日付・**今日の来店の集計**（来店の組数・買取の件数・成約率・買取額）が出る。成約率 ＝ 買取に至った数 ÷ 完了した数。**取消・来ずは来店に数えない**。
- 見本の来店は、記録が空のときだけ自動で入る（店舗ごとに、待ち・予約・完了）。「（デモ用）データ初期化」で来店の記録・作業中の内容が消える（店舗マスタは消えない）。

### 11.2 来店（一覧）

- **状態**: 予約 → 待ち（来店済み）→ 対応中（担当の店舗スタッフが付く）→ 完了。ほかに**取消**（理由つき。予約・待ちのみ）・**来ず**（予約の日になった予約だけ）。
- **予約**は、コールセンターの来店予約（2.6）から来る。店舗では、**来店済みにする**／**対応を始める**（来店済みを省いて、予約から直接でもよい）／来ず／取消ができる。
- **飛び込み**: 予約なしの来店。**お名前だけで受け付けられる**（電話番号は、聞ければ。過去のお客様を探す手がかり）。受け付けると「待ち」に並ぶ。
- 一覧は、待ち（来店順）・対応中・これから来店の予約（時刻順）・完了（買取の金額、または「見送り」）・取消と来ず。**過去のお客様には、顧客ランク・厄介度・クーリングオフ歴の印**が付く（電話番号が一致したとき）。
- 対応中の来店は、**どの店舗スタッフでも「買取を続ける」で開ける**（交代・引き継ぎのため）。作業の内容は、来店ごとに保存され、画面を閉じても続けられる。

### 11.3 買取の流れ（5手順）

営業タブレットの現地買取（1.6）と同じ考え方で、店頭に合わせて整理した。

1. **お客様確認**: 初めて／リピーター（何回目）、過去の評価（顧客ランク・厄介度・クーリングオフ歴）、前に査定したが売らなかったもの（見送り品）を、スタッフが見る（お客様には見せない）。お客様の情報（**氏名・電話番号・住所・生年月日が必須**、フリガナ・予備の電話番号・郵便番号・職業）を、本人確認書類と照らして入力し、「確認した」にチェックして次へ。
2. **説明事項**（査定前に必須）: 5項目（買取の流れ・断れること・撮影と写真送信の了承・本人確認の必要性（古物営業法）・**店頭買取はクーリング・オフの対象外であること**）と、**他商品を提案してよいか**の回答（はい・いいえ）。
3. **買取明細**: 商品マスタから選ぶ（検索）。金額は**1点あたり（単価）**を入力。ランク・数量・**売る／見送る**を決める。見送る商品は契約に入らず、見送り品として記録される。**売る商品が1点もなければ、次へ進めない**（その場合は「買取に至らず終了（見送り）」）。
4. **シール**: 売る商品の**1点ごとに、シールNo.と色**（紫・赤・黄緑青）が必要（読み取りはモック）。同じシールを別の商品には使えない（入庫待ち済みのシールも）。紫・赤は高額品で、いったん倉庫に入庫してから本社へ移す（5.2）。
5. **確認・支払い**: **お客様に見せる**買取内容と支払い金額。**契約をGMOサインへ送る**（本人確認書類の登録・契約書の印刷。チェック項目・署名は、印刷した紙にお客様が記入。6章）。そのあと、**終了前の確認6項目**（本人確認書類・契約書の記入・店舗控えの回収とお客様控えの手渡し・代金のお支払い・数量の一致・忘れ物）がすべて済むと、**買取を完了**できる。
   - **契約を送ったあとは、前の手順に戻れず、見送りにもできない**（契約書と食い違わないように）。
   - 訪問買取の「梱包・持ち帰り」「クーリング・オフの説明」は、店頭にないので、確認項目から除いた。

**買取に至らなかった場合**: どの手順からでも「買取に至らず終了（見送り）」で完了にできる。入力済みの商品は、すべて見送り品として記録され、成約率の分母（完了）に数えられる。

### 11.4 完了すると作られる記録

- **契約**: 訪問買取と同じ契約の記録（`channel: store`・店舗・来店のID）。GMOサイン（6章）で印刷でき、**お客様の履歴は電話番号で結びつく**ので、次回は「リピーター」になる（訪問買取・店頭買取をまたいで同じお客様として数える）。契約書の「新・再」と「鑑定士」は、リピーターか／担当の店舗スタッフ。
- **入庫待ち**: シールを貼った実物**1点ごと**（営業の持ち帰りと同じ。5.2）。店頭買取の印・店舗・店舗スタッフが残る。倉庫・物流の「入庫」に出て、倉庫担当が入庫する（高額品の規則は5.2のまま）。倉庫の画面には、担当が「**なんば店・店舗スタッフ 田中 美咲**」のように出る（営業の名簿では引かない）。
- **見送り品**: 売らなかった商品（売らなかった理由は聴取しない＝記録しない）。次回、お客様確認で出る。

### 11.5 モックの範囲

連動は最小限。**レジ現金・査定部との連動・経理部・業績の店舗別・納入先の倉庫への連動・古物台帳**は、まだない（10章）。
