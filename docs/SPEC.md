# 出張買取アプリ（モックアップ）機能仕様書

このリポジトリを引き継ぐ方向けに、これまでの依頼内容を機能ごとに整理した仕様書です。
**「なぜそうしているか」（業務上の前提・決定の経緯）を中心に**まとめています。コードを読めば分かることは省き、迷いやすい点を残しています。

- 記録日: 2026-10-25（git履歴 2026-10-21〜10-25 の127コミットと、依頼時のやり取りから整理）
- 現状: **モックアップ**です。外部サービス・サーバーはなく、すべて localStorage とダミーデータで動きます。
- 関連資料: 画面の使い方の詳細は [README.md](../README.md)（特に「倉庫・物流」の節が詳しい）。振る舞いの正は `tests/` のテスト（`npm test`、282件、全件成功を確認済み）。
- 本書とコードが食い違ったときは、**テストとコードが正**です。仕様を変えたら本書も更新してください。

### 0.2 業務の流れ（全体）

```
お客様の電話
  → [コールセンター] 聞き取り・エリア判定・担当営業の仮決定 ＝ 仮確定（オペレーター）
  → [配車確定] 配車係が翌々日分などを確定
  → [営業タブレット] 予定に出る → 始業 → 訪問 → 現地買取 → 訪問終了
        ├ 査定は [本社 査定部] が承認・助言
        └ 契約書は [GMOサイン] で印刷し、紙で署名
  → 持ち帰り（入庫）→ [倉庫・物流] 保管（10日間はクーリングオフ期間）
  → 出品・委託・直接販売 → 購入者・業者へ発送 → 売上・利益の管理
  → （クーリングオフ）お客様の電話 → [コールセンター] 依頼を作成 → [倉庫] 回答・返送 → 返金の確認で完了
  → 終業・日報 → [経理部] で現金・経費を確認
```

### 0.3 技術と構成

- Vite + vanilla JS（フレームワークなし）+ Tailwind CSS（CDN。**ネット接続が必要**）。
- 画面間の連携は、同一ブラウザの localStorage を介します（別タブで開いて確認）。キーは `src/store.js` に集約。
- ロジックは画面から独立した純関数にして `src/` に置き、`tests/` で検証しています。画面は各ディレクトリ（`callcenter/`・`honsha/`・`accounting/`・`warehouse/`・`gmosign/`・`tablet/`）。
- 各画面下部の「（デモ用）データ初期化」で、マスタ以外を消せます。倉庫マスタは消えません。
- 起動は `docker compose up --build`（http://localhost:5173）。Docker を使わない場合は `npm install` のあと、`package.json` の dev スクリプトで開発サーバーを起動。テストは `npm test`。

### 0.4 ダミーであるもの（本実装で置き換える対象）

| 対象 | 現状 |
|---|---|
| ログイン（営業・倉庫担当） | ID・パスワードは何でも通る。SMSは送らず画面に認証コードを表示 |
| AI査定・レシートOCR・AIカメラ | 画像のハッシュから、それらしい値を返すだけ（`src/ai.js`） |

| GMOサイン | 実サービスとは無関係の画面 |

## 1. 営業タブレット（`/tablet/`）

### 1.1 ログイン

- ID・パスワード → SMS認証コード（2要素認証）。パスワード再設定もSMSコードで本人確認する。
- コードは6桁・有効5分・再送は30秒待ち・入力ミスは3回まで（`src/auth.js`）。
- パスワード条件: 8文字以上・英字と数字を含む・IDと同じ不可。
- 存在しないIDでも、画面上は同じように進める（ID有無を知られないため）。
- モックのため、IDは何でも可。既存IDならその営業、それ以外は先頭の営業（鈴木 一郎）としてログイン（デモ用アカウントは `sales01`〜）。
- **初期画面は状態で切り替わる**: 未ログイン→ログイン、始業前→始業、始業済み→ダッシュボード。データ初期化でログイン状態も破棄。

### 1.2 メインメニュー（左の開閉式ドロワー）

ダッシュボード／始業／今日の予定／現地買取／経費管理／商品の持ち帰り／終業・日報。
始業と終業・日報は別項目で、状況に応じて活性・非活性が切り替わる。

### 1.3 始業・終業と経費（`src/workday.js`）

**重要な決定**: 始業するまで**現地買取だけ**が使えない。他の機能は始業前・終業後も使える。

- **始業**: 前日繰越金を実際に数えて照合（**ずれがあれば理由が必須**）→ 点検8項目（飲酒・体調・身だしなみ・社員証・車両・タブレット・買取用資材・本社からのお知らせ）をすべてチェック → 記録して業務開始。
- **所持金** ＝ 前日繰越金 ＋ 本社からの入金 − 経費。毎朝の定例入金（30万円）はダミー。繰越金の初期値は5万円。
  - **未始業の営業にも、前日繰越金は手元にある**ものとして扱う（経理部の画面でも同様）。
- **経費**: 種別（ガソリン代・昼食代・備品購入・高速/駐車場・交通費・その他）＋金額＋レシート写真。レシートはAIで読み取り、種別・金額・内容を自動入力（人が確認・修正できる前提。撮影が先頭）。数字は右詰め。
- **買取代金は、訪問終了時に経費として自動計上**される（所持金から減る）。経費の集計・「高額」判定からは除外される。
- **終業**: 帳簿残高と実際の現金を照合（ずれは理由必須）→ 終業点検4項目 → 日報提出。日報には現金収支・経費内訳・訪問と買取の実績が自動集計される。**終業後は、現地買取と経費の計上ができない**。翌日の繰越金は、終業時に数えた金額。
- **訪問できなかった場合**: 不在／日程変更の依頼／お客様都合のキャンセル／その他（その他はメモ必須）。**訪問実績には数えるが、営業の責任ではないため業績（成約率など）に影響しない**。日報・本社画面に反映される。

### 1.4 ダッシュボード・メッセージ・業績

- 本社からのメッセージとグループリーダーからのメッセージを、別枠・開閉式で表示。枠は2件分の高さに固定し、詳細はモーダル。「他○件あります」を表示。重要フラグ・既読管理あり。宛先は「全員」または「グループ」。
- **業績ダッシュボード**: 今日／今週／今月。訪問数・契約数・買取額・成約率・平均単価。月間目標に対する進捗とペース。
  - **閲覧権限**: 一般は自分のみ。**グループリーダーはグループ全員・メンバー個別も閲覧可**（デモ用にロール切替あり）。
  - 訪問ごとの結果モーダル、期間中の日報の閲覧（リーダーはメンバーの日報も）。
  - 業績データはすべて、ユーザー×日付から決まる疑似乱数のダミー（日曜と未来日は休み扱い）。
- グループは A（東日本）/ B（西日本）、営業は16名（`src/dashboard.js`）。

### 1.5 今日の予定・ルート確認

- **前日（実績）・今日・明日の3日表示**（明後日は非表示）。未訪問・訪問中・完了を色とバッジで区別。訪問済みをタップすると結果の詳細。
- ルート確認は予定画面に統合。2件目以降の出発地は「前の予定の場所／現在地」で切り替え。
- 予定の詳細・訪問開始画面で、**受電時のヒアリング**（コールセンターの入力内容）と、**お客様のランク・厄介度・クーリングオフ歴・見送り品**を確認できる。
- コールセンターで**確定**した予約だけが予定に出る（仮確定は出ない）。

### 1.6 現地買取の流れ（`src/views.js` の `STEPS`）

訪問開始 → お客様確認 → 説明事項 → 買取明細 → 買取商品の確認 → シール紐づけ → 送信・終了

1. **お客様確認**: 初めて／リピーター（何回目）を表示。リピーターは過去の買取履歴・評価を確認できる。
2. **説明事項**（査定前に必須）: 5項目（買取の流れ・断れること・撮影と写真送信の了承・本人確認の必要性（古物営業法）・クーリング・オフ）を説明してチェックし、**他商品を提案してよいか**をお客様に確認する。両方済むまで次へ進めない。
3. **買取明細**: 商品マスタから選択／AIカメラ／本社査定の依頼／AI査定。金額は通貨形式（¥・円・3桁区切り）。明細の段階でもシールを貼りながら進められる。
   - 査定依頼は本社査定部へリアルタイムに届き、回答（コメント・提案額）が返る。コメントのタグは「安すぎる／高すぎる／要再確認／その他」。未確認のコメントは商品に❗が出る。
4. **買取商品の確認**: **お客様に見せる画面**（文字は大きめ）。承認済みと確認中を一目で区別。**査定部の承認が必要**。承認後に金額・ランク・数量が変わったら、再承認が必要（`stale`）。
5. **シール紐づけ**: 商品1点（数量があれば1個ずつ）にシールのQRを読み取って紐づける（カメラ起動はモック）。**シールの色（紫・赤・黄・緑・青）を選ぶ（選ばないと次へ進めない）**。同じシールを別の商品に使うとエラー。
6. **送信・終了**: 訪問終了前チェックリスト（本人確認書類の登録・契約書の印刷と紙の署名・会社控えの回収・クーリング・オフ説明・代金のお支払い・梱包・数量一致・忘れ物の8項目）。GMOサインへ送信して訪問終了。
   - 契約書は、GMOサインで印刷する。**チェック項目・署名は、印刷した紙にお客様が記入する**（電子署名ではない）。
   - 訪問終了時に、シール付きの実物1点ごとに「入庫待ち」が登録される。
   - **査定したが売らなかったもの（見送り品）**を記録できる（売らなかった理由は聴取しない＝記録しない）。

### 1.7 お客様の評価（営業の記録）

- 営業が訪問ごとに記録する。**お客様には見せない**。総合★1〜5、態度（良好/普通/難あり）、リピート見込み、資力（高そう/普通/低そう）、次回時期、次回の商材、特記事項、メモ。
- **評価はアポ（訪問）単位と、お客様単位の2種類を分けて管理**する。営業のタブレットはアポごと。お客様単位は配車係が登録する。
  - 初回アポの評価は、お客様の評価が未登録なら、**お客様の評価の初期値に自動設定**される（2回目以降は自動設定しない）。

### 1.8 商品の持ち帰り（入庫）

→ 詳細は 5.2。営業が自分の商品を、納入先の倉庫を選んで入庫する。**高額品（紫・赤）は営業のタブレットからは入庫できない**（「高額品 → 本社へ」と出る。本社へ郵送・持参し、本社で入庫）。

## 2. コールセンター（`/callcenter/index.html`）

運用の前提は次のとおり（ユーザーからの指示。自動メモリにも記録済み）。**ここを外すと、後で連絡し直しが発生する。**

> **オペレーターは「仮確定」まで。** 担当営業も仮決定で、**お客様には営業の名前を伝えない**（日時だけ伝える）。
> **配車係が最終確定**する。主に**翌々日分を毎日**。確定した訪問だけが営業タブレットの予定に出る。
> 受付関連の画面・文言では「確定」ではなく**「仮確定」**を使う。営業名をお客様向けに出さない。

### 2.1 受付（オペレーター）

- **ヒアリング項目**（`callcenter/intake.js`）: 電話番号1・2、姓名（別入力）、フリガナ（必須）、性別（必須）、年齢（必須）、郵便番号、住所、希望日時、来電のきっかけ（チラシ）、売りたいもの、当日の立会い、ご同席者、大型品、駐車スペース、表札、前日確認の連絡時間帯、訪問時の注意。
  - **必須（確定に必要）**: 電話番号・お名前・フリガナ・性別・年齢・住所・来電のきっかけ・売りたいもの。他は聞き忘れの注意だけ。
  - **聞き取り状況**（聞いた✔／未）を項目ごと・上部パネルに表示して聞き忘れを防ぐ。「なし」と聞いた場合も聞いた扱い。必須は赤い＊。
  - **年齢を聞けなければ、声色から性別・年代を推測**して選べる。ただし**「推測」として区別して記録**する。
  - 立会いとご同席者は別項目。売りたいものは、メイン商材（背広・婦人服・婦人靴・紳士靴、数量帯）＋その他の商材＋詳細（複数行）。
- **来電のきっかけ**: チラシは**固有のID**（N/P/D＋4桁）で特定する（広告の種類だけでは、どの号か決められないため）。IDのない広告（ネット・テレビ・紹介・再利用）のみ言葉から判定。
- **過去のお客様**: 電話番号（1・2）が一致すれば、情報を引用できる。直近の買取額・依頼回数・総買取額、**電話番号ごとの受電履歴**を表示。オペレーター向けの表示は最小限。
- **エリア判定**（`src/dispatch.js`）: 訪問先の**都道府県**から担当エリアを決め、そのエリアの営業だけを候補にする（電話は全国から来るため、お客様の住所で判定）。

  | エリア | 都道府県 |
  |---|---|
  | 大阪 | 大阪・奈良・和歌山 |
  | 兵庫・京都 | 兵庫・京都・滋賀 |
  | 関東 | 東京・神奈川・埼玉・千葉・茨城・栃木・群馬 |
  | 東海 | 愛知・岐阜・三重・静岡 |

  担当のない都道府県は「対応エリア外」とし、他エリアの営業を例外として選べる。**判定は提案**で、オペレーターがGoogleマップで位置を確認してエリアを確定する。
- **空き確認**: 営業時間 9:00〜19:00、30分刻み、訪問は60/90/120分。**訪問の前後30分は移動時間として確保**。営業の予定と確定済み予約から空きを判定。欠勤は選べず表示。**午後出社・午後半休**も反映（休みの時間にはアポが入らない）。空き開始時刻は人数つきで一覧。
- **カレンダー**: 1週間ごとの週表示（1行の一覧）と、日別表示（営業ごとの列）。営業の顔写真・ランク・得意分野・前のアポからの距離（前のアポがなければ距離は出さない）を表示。**どの枠を選ぶかはオペレーターが決める**（システムが候補をあらかじめ選ぶのはOK）。
- **公平な配分**: **女性のお客様は客単価が高いため、今月の「女性のお客様の担当件数」が少ない営業をおすすめ**する（男性のお客様は担当件数の少ない順）。おすすめ以外を選ぶと、より担当の少ない営業がいることを知らせる。
- **営業にはランク（S〜C、仮の設定）と得意分野**がある。大阪エリアは営業10名。実績・担当件数はダミー。
- **仮確定**: 通話を終えても**自動確定しない**。枠と担当の最終決定はオペレーターが行う。

### 2.2 仮確定後の変更・取消（折り返しの電話）

お客様から「やっぱりやめる」「日を変えたい」と電話が来ることがある。

- 電話番号で既存の受付を見つけ、**全項目を変更**・取消ができる。取消は**理由つきで記録を残す**（理由: お客様のご都合・入力ミス/重複・会社の都合・その他）。履歴が残る。
- **確定済みをオペレーターが変更すると、仮確定に戻り、配車係に知らされる**。

### 2.3 配車確定（配車係）

- 営業ごとの列のカレンダーのみ（一覧表示は廃止）。**予約をドラッグして営業・時間を調整**できる。営業の元からの予定も予約として取り込んで動かせる。
- 色: 仮確定=薄い青／確定済み=濃い青。「未確定の仮確定」と「確定から仮確定に戻ったアポ」は色分けし、変更内容をカレンダー下の詳細に表示。休みと重なる予定は警告。
- アポ間の移動距離と、営業ごとの1日の総移動距離を表示。営業のランクと今月の担当件数の偏りを見て判断する。
- **お客様の詳細モーダル**（配車係が誰を当てるかを判断する材料）: 買取履歴（品目ごと全件・折りたたみ）、営業の評価・メモ（アポごと）、前回までの担当、ランク・厄介度・クーリングオフ歴、見送り品。
  - **顧客ランク**（S〜C）: 登録がなければ、**総買取額から自動**（100万円以上=S、50万=A、20万=B、実績あり=C、なし=新規）。
  - **厄介度**（なし/注意/要注意）: **人が登録したものだけ**。営業の評価から自動で上げない（自動判定は廃止した）。
  - **クーリングオフ歴**は契約の記録。お客様の評価を登録し直しても消えない。
- **配車係の権限ルール（重要）**: 確定権があるので、**配車係が何を入力・変更しても、状態は変えない**（確定済みは確定のまま）。お客様に連絡して回答次第で決めたいときだけ、配車係が意図的に**「仮に戻す」（確認待ち）**。
- 「空き状況・受付履歴」画面は削除済み。

### 2.4 音声入力デモ（今後の拡張）

通話デモは別ウィンドウ（`?demo=1`）。台本を1発話ずつ／最後まで一気に進められ、お客様の発話から項目を拾って入力欄に自動セットする。**あくまでデモ。基本はオペレーターの手入力で完結させる**前提で、デモは通話終了でも訪問を自動確定しない。

### 2.5 クーリングオフの受電と依頼（`?tab=cooloff`）

クーリングオフは、**お客様から電話がかかってきて始まる**（専用の番号。受けるのはコールセンターのオペレーター）。**依頼を作るのはコールセンター、返送・完了の対応をするのは倉庫**。（以前は倉庫担当が返品を「受付」していたが、依頼に一本化した。倉庫の画面に受付の入力欄はない。）

> お客様の電話 → オペレーターが商品を検索し、状態を確認 → **依頼を作成**（システム上で倉庫へ問い合わせ）→ 倉庫が回答 → 返送 → お客様の手元に商品が戻り、**買取代金の返金**も済んで**完了**。進捗は依頼ごとに管理する。

- **商品の検索（オペレーターが探しやすいUI）**: お客様は、手元に商品がないまま「先週の金曜日に来てもらった山田ですが、そのとき売った時計を返してほしい」のように、**うろ覚えの手がかり**で電話してくる。**実際には買い取っていない可能性**や、**似た商品が複数あってそのうちの1つだけ**の可能性もある。そのため、次の点を守る。
  - **商品の写真を、検索結果に大きく出す**（押すと拡大）。**写真を見せながら「これですか」と確認**できないと、電話の会話が成り立たない。写真は、**倉庫で登録した写真**（5.3）、なければ買取のときの査定依頼の写真、それもなければ商品名から作ったダミー（モック）を使う。本実装では、買取時の撮影写真を商品に必ず紐づける前提。倉庫の依頼の画面にも写真を出す（棚から探しやすい）。
  - **手がかりはどれでも探せる**: **電話番号**（買取データは、訪問（アポ）→お客様を通じて、受付でヒアリングした電話番号1・2に紐づく。モックでは、買取のとき商品に番号を控える。ハイフンの有無・4桁以上の一部でも可）・お名前（空白の有無を問わない。同じ名字が複数いても、買取日で絞れる）・シールNo.・商品名・商品の種類（「時計」でカテゴリにも当たる）・**買取日**（直近14日を「10/24(金)」のように曜日つきで並べ、その日の契約の数を添える。複数選べる）・商品の種類のボタン。名前を外して買取日だけ、でも探せる。種類を選ぶと、その商品だけを出す。
  - 結果は契約（お客様・買取日）ごとにまとめ、商品ごとに状態の目印を出す: 在庫・期間内／**期間超過**（倉庫が個別に判断）／出品中・委託中・入庫前など（倉庫に確認）／**売却済み（対応不可）**／すでに依頼中／返品済み／輸送中・梱包中（届く・発送が済むまで依頼できない）。
  - 見つからないときは、「買い取っていない可能性もある」ことと、探し直す方法（名前を外す・買取日を広げる）を知らせる。
- **依頼の作成**: 商品・電話番号・理由・受電メモ・受けたオペレーター（受付者）を記録。依頼は**倉庫ごとに分かれる**（5.7）。売却済みの商品は、対応不可の依頼として記録だけ残す。
- **倉庫の回答**（5.7）で、返送できれば返送の準備へ、**対応できなければ理由つきで「対応不可」**として終わる。オペレーターは進捗を見るだけで、回答・返送・完了の操作はできない。
- **進捗の段階**: 受電・依頼 → 倉庫の回答 → 返送 → 代金の返還（`returnSteps`）。倉庫の回答待ちの件数が、タブに出る。

## 5. 倉庫・物流（`/warehouse/index.html`）

営業が入庫した買取商品（シールNo.ごとの実物1点）を、フリマ・業者に販売して利益を得るための画面。**画面ごとの操作は README の「倉庫・物流」の節が詳しい**ので、ここでは決定事項（ルール）を整理する。ロジックは `src/warehouse*.js`・`src/shipping.js`・`src/stock.js`。

### 5.1 ログインと倉庫マスタ

- 担当者ごとにログイン（`wh01`〜`wh05`、パスワードは何でも可）。**所属する倉庫が、入庫先と表示の対象**になる（上部の「対象の倉庫」で全倉庫・他倉庫に切替可）。操作はログインした担当者の名前で記録される。
- **倉庫は営業所とは独立した施設**として管理（全国に複数）。営業所と一体／倉庫のみ／倉庫のない営業所（営業のみ）がある。初期値: 大阪倉庫（大阪営業所と一体）・関東倉庫（関東営業所と一体）・福岡倉庫（倉庫のみ）・本社。**兵庫・京都、東海の営業所には倉庫がない**。
- 倉庫ごとに名前・郵便番号・住所・電話番号（**伝票・CSV出力に必要**）・営業所との関係・保管場所（棚）・有効/無効を登録。**保管中の商品や有効な担当者がいる倉庫は無効にできない**。担当者は各倉庫に所属（登録・所属変更・有効/無効）。
- **委託先（業者）**も同じ画面で登録（名前・郵便番号・住所・電話番号。初期値は大阪時計オークション・東京ブランド市場・関西貴金属市場）。
- マスタは「データ初期化」では消えない。メニューは左上「☰」の開閉式。入庫待ち・受け取り待ち・返品対応中の件数がメニューに出る。

### 5.2 入庫と、シールの色・高額品

- **本社も保管場所の1つ**（倉庫マスタに1か所だけ）。**シールの色が紫・赤の高額品は、納入のときから本社**に入る（10日待ってから郵送するのではない）。それ以外は倉庫。
  - 色は紫（最も高額）・赤・黄・緑・青の5色だが、**システム上は「紫」「赤」「その他（黄・緑・青）」の3つ**。本社に納入する色は倉庫マスタ画面で変更できる。
  - 色は基本的に営業が決める（査定部と相談することもある）。
  - 1契約に高額品とそれ以外が混ざる場合、高額品だけ本社、それ以外が倉庫に入る。
- **入庫の権限**: 本社の担当者は高額品だけ、本社以外の担当者は高額品以外だけ入庫できる。**倉庫間の移動も同じ規則**（高額品は本社以外へ移せない）。
- **倉庫担当の入庫**: 契約ごとに、明細と実物を見比べて、一致した商品に☑を付けてから入庫。☑は誰がいつ付けたかが残る。スキャナ・手入力（シールNo.）の場合は「読み取りで照合した」記録。誰が買い取った商品でも入庫できる。入庫先の棚を選んでから入庫。
- **営業の入庫**（タブレット）: 自分の商品を、納入先の倉庫を選んで入庫（初期値は自分の営業所と一体の倉庫）。この場合、倉庫での照合の記録は残らない。入庫済み・他の営業の商品・未登録のシールはエラー。手元にない商品は「所在不明」として報告できる。対象日で絞り込み（1日分でも、2〜3日分まとめてでも可）。
- **シールの貼り替え**: 色が間違っていた場合、**シール自体が別になるので、商品のシールNo.（ID）も新しくなる**。古いNo.・色は履歴に残り、移動などの記録は新しいNo.に引き継がれる。古いシールを読み取ると、貼り替え済みと新しいNo.が出る。**貼り替えられるのは、入庫前・所在不明・在庫の商品のみ**（出品中・委託中・売却済み・返品対応中・輸送中は不可）。納入先が変わる場合は、倉庫間移動で本社・倉庫に移すよう案内する。営業は訪問を終える前なら、タブレットでシールを「解除」して読み取り直す。

### 5.3 商品管理

- 状態: 入庫待ち／在庫／出品中／売却済み／返品。検索は**1つの欄**（商品名・シールNo.・お客様名。QRリーダー・手入力のEnter・カメラ（モック）で読み取れる）。読み取ると、詳細と、買取から入庫・出品・売却・返品までの履歴を表示。
- 表示は「一覧」（初期表示）と「買取日・お客様別」（契約単位にまとめる。クーリングオフ時にすぐ探せる）。QRで探すと、**同じ契約で買い取った他の商品とその保管場所**も出る。
- **商品の写真の登録（倉庫）**: クーリングオフの電話で、お客様と商品を確認するための写真。商品管理の一覧・詳細、入庫の一覧の写真を押すと、撮影・選択して登録（撮り直し）できる。**誰がいつ登録したか**が残る。削除するとダミーの絵に戻る。**未登録は印（未登録）で見分けられ、「写真未登録」で絞り込める**。在庫の操作ではないので、**どの倉庫の商品でも登録できる**（5.5 の制限の対象外）。
- ページ送り: 20/50/100点（買取日・お客様別は契約の件数で分割）。絞り込み・検索・表示切替で1ページ目に戻る。

### 5.4 パックの流れ（共通）

倉庫間移動・委託・購入者への発送は、**同じ「パック」の流れ**で統一している（`src/shipping.js`、画面は `warehouse/packUi.js`）。

> ① 商品を探して入れる（検索・QR読取）→ ② パッキング（配送業者・サイズ60〜170・個口数・メモ）→ ③ 明細（書類）を出力 → ④ 発送伝票とCSVを出力 → 発送（追跡番号）

- 配送業者はヤマト運輸・佐川急便・日本郵便・その他。CSVは各社の取込用（UTF-8、個口ごとに1行、複数パックのまとめて出力可。**列の並びは仮で、実際の取込形式に合わせて調整が必要**）。
- 梱包中の商品は「梱包中」になり、出品・返品・別のパックには使えない。入れられない商品は理由が出る（登録なし・貼り替え済みの古いシール・在庫でない・他の倉庫・別のパック・送り先の規則違反）。
- 明細・伝票の出力は日時が記録され、**未出力のまま発送するときは確認が出る**。送り先の郵便番号・住所・電話番号が足りないと、伝票・CSV出力のときに知らせる。

| パックの種類 | 書類 | 載せるもの／載せないもの | 発送後 |
|---|---|---|---|
| 倉庫間移動 | 送付明細 | 商品・買取額・合計・受領確認欄 | 「輸送中」。受け取るまで**どちらの在庫にも数えない**。送った倉庫は輸送中なら取り消せる |
| 業者への委託（業者オークション） | 委託明細 | **希望価格のみ。原価・お客様の情報は載せない** | 「委託中」（倉庫の外）。売れたら入金額を登録（委託手数料を引いて売上に反映）、売れ残りは倉庫の在庫に戻る |
| 購入者への発送（フリマ・業者直接販売） | 納品書 | **商品名と売価のみ。原価・買い取ったお客様・シールの色は載せない**。敬称は「様」 | 売却済みのまま。発送日時・追跡番号が履歴に残る。購入者情報は梱包中に直せる |

- 移動先の担当者は、届いた商品に☑を付け、自分の倉庫の棚を決めて受け取る。送れるのは在庫だけ（出品中・委託中・返品対応中は先に戻す）。
- 委託の希望価格は、原価の1.3倍の目安が入る。高額品も委託できる（納入先の規則は倉庫間の移動のみ）。
- 委託先の市場で売れた商品は、市場が購入者へ送るため、購入者への発送の対象外。
- サンプルデータでは、どの倉庫・本社の担当者でログインしても、梱包中・受け取り待ち・輸送中・履歴のダミーが見える。

### 5.5 自分の倉庫の商品だけ扱える

出品・売却・価格変更・返品の対応は、**ログインした担当者の所属倉庫の商品だけ**。他の倉庫の商品は、先に倉庫間移動で自分の倉庫に移す（商品管理では他倉庫の商品も見られる）。

### 5.6 販売（出品）・売上管理

- 販売先と手数料率（**ダミー**）: メルカリ10%・ヤフオク10%・ラクマ6.6%・業者オークション3%（委託）・業者へ直接販売0%。売れたら、実際の売価・送料・購入先を登録（手数料は料率で自動計算）。出品中の価格変更・取り下げも可。
- **出品価格の目安は原価の1.3倍**（千円単位に切り上げ）。
- **売上管理**: 今日・今月・全期間の売上・原価・手数料・送料・利益・利益率を、販売先別・カテゴリ別に集計。集計対象は自分の倉庫（初期値）／他の倉庫／**会社全体**（倉庫別の内訳も出る）。

### 5.7 クーリングオフ返品

- 法律上は書面を受け取った日（買取日）から**8日間**。お客様の通知は郵送で届くため、余裕を見て**買取から10日間（`COOLING_OFF_DAYS`）は販売せず保管**する。
- 保管期間中の商品は**出品できない**（「○/○まで出品不可」と表示）。期間を過ぎた入庫済みの商品から出品できる。
- **依頼はコールセンターが作る**（2.5）。倉庫の画面は、その依頼への対応だけを行う（受付の入力欄はない）。依頼は問い合わせを受ける倉庫（入庫前の商品は納入先になる倉庫、高額品は本社）ごとに分かれ、`groupId` で同じ契約として結びつく。
- 流れ: **倉庫に問い合わせ中** → 倉庫が回答 → **返送の準備中** → **返送済み**（追跡番号）→ **お客様からの買取代金の返還を確認して完了**。完了した商品は「返品済み」で在庫から外れる。理由: 家族に反対された／金額に納得できない／手放したくなくなった／その他。
- **倉庫が対応できないと回答**したときは、**理由が必須**で「対応不可」になり、商品は元の状態に戻る（そのあとで改めて依頼もできる）。**売却済みの商品**の依頼は、回答を待たず「対応不可」として記録する。
- **期間を過ぎた商品も依頼は作れる**（「期間超過」の印が付く）。受け付けるかは倉庫が個別に判断する。出品中・委託中・入庫前などの商品も、依頼を作って倉庫が回答する。**輸送中・梱包中の商品は、届く・発送が済むまで依頼できない**（移動・委託・発送のパックを壊さないため）。
- 問い合わせ中は、在庫の商品だけ出品できなくなる（ほかの状態の商品は、倉庫が「返送できる」と回答するまで状態を変えない）。
- 契約の商品が複数の保管場所（本社と倉庫）に分かれていても、**契約全体で依頼を作り**、保管場所ごとの返品に分かれる（お客様に返していただく代金は契約全体の合計）。それぞれの担当者が回答・返送・完了の対応をする。他の倉庫の依頼は扱えない。
